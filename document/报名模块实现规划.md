# 报名模块实现规划

> 日期：2026-06-28  
> 目标：在当前认证、安全、方向管理、时期管理基础上，接入用户侧报名模块

---

## 1. 本文档目的

本文档用于明确“报名模块”在当前代码基线下的实现范围、实现方式、接口设计、校验规则、测试方案和开发顺序。  
待确认后，再进入正式编码阶段。

## 2. 当前项目基础与可复用能力

当前仓库已经具备以下可直接复用的基础设施：

- 登录态获取：`CurrentUserService`
- 时期校验：`PeriodService.ensureRegistrationOpen()`
- 统一响应：`ApiResponse`
- 统一异常：`BusinessException` 体系
- 统一鉴权：Spring Security + `AuthzService`
- 已有数据表：`application`、`group_member`、`direction`
- 已有方向模块：可校验一级/二级方向关系

这意味着报名模块不需要重新设计认证和权限体系，重点是补齐：

- 报名 Controller
- 报名 Service
- DTO / VO
- `ApplicationRepository` 查询能力
- 报名相关单测与集成测试

---

## 3. 本轮实现范围

本轮建议只接入“用户侧报名主流程”，不把管理员报名管理一并混进来。

### 3.1 本轮包含

- `GET /api/v1/applications`
- `GET /api/v1/applications/{id}`
- `POST /api/v1/applications`
- `PUT /api/v1/applications/{id}`
- `DELETE /api/v1/applications/{id}`
- `GET /api/v1/applications/summary`

### 3.2 本轮不包含

- 管理员报名列表与筛选扩展
- 报名导出
- 报名审核/驳回
- 报名与分组的联动写接口
- 可配置的报名年级白名单

说明：

- “管理员查看全部申请”需求后续可并入管理端用户/报名管理模块
- 当前优先把“新生可报名、可修改、可撤回、可查看状态”闭环跑通

---

## 4. 功能目标

报名模块完成后，普通登录用户应具备以下能力：

1. 查看自己的报名申请列表
2. 查看自己某一份报名申请详情
3. 在报名期提交一份报名申请
4. 在报名期修改自己尚未分组的报名申请
5. 在报名期撤回自己尚未分组的报名申请
6. 查看报名汇总信息，例如申请数、已分组数、所属分组

---

## 5. 接口规划

### 5.1 `GET /api/v1/applications`

用途：

- 获取当前登录用户自己的报名申请列表

返回建议：

- 返回数组，不分页
- 默认按 `createdAt desc`

每项建议包含：

- `id`
- `realName`
- `phone`
- `college`
- `major`
- `className`
- `grade`
- `admissionYear`
- `directionLevel1Id`
- `directionLevel1Name`
- `directionLevel2Id`
- `directionLevel2Name`
- `introduction`
- `status`
- `statusRemark`
- `groupId`
- `groupName`
- `createdAt`
- `updatedAt`

### 5.2 `GET /api/v1/applications/{id}`

用途：

- 获取当前登录用户自己的某一份报名申请详情

权限建议：

- 本轮仅允许申请本人访问
- 未来如需要负责人查看，可继续沿用 `AuthzService.canAccessApplication(...)`

### 5.3 `POST /api/v1/applications`

用途：

- 创建报名申请

请求体建议：

- `realName`
- `phone`
- `college`
- `major`
- `className`
- `grade`
- `admissionYear`
- `directionLevel1Id`
- `directionLevel2Id`
- `introduction`

### 5.4 `PUT /api/v1/applications/{id}`

用途：

- 修改自己的报名申请

请求体与创建接口一致。

### 5.5 `DELETE /api/v1/applications/{id}`

用途：

- 撤回自己的报名申请

实现方式：

- 逻辑撤回，不删记录
- 将 `status` 置为 `WITHDRAWN`

### 5.6 `GET /api/v1/applications/summary`

用途：

- 返回当前用户报名概览

建议返回：

- `applicationCount`
- `submittedCount`
- `groupedCount`
- `groupIds`

可选补充：

- `withdrawnCount`
- `rejectedCount`

本轮建议先严格对齐现有 API 文档，额外字段先不加。

## 7. Repository 扩展规划

当前 `ApplicationRepository` 只有很少的统计方法，报名模块至少需要补以下能力：

- `List<Application> findAllByUserIdOrderByCreatedAtDesc(Long userId)`
- `Optional<Application> findByIdAndUserId(Long id, Long userId)`
- `boolean existsByUserIdAndDirectionLevel2Id(Long userId, Long directionLevel2Id)`
- `boolean existsByUserIdAndDirectionLevel2IdAndIdNot(Long userId, Long directionLevel2Id, Long id)`
- `long countByUserIdAndStatus(Long userId, ApplicationStatus status)`

`GroupMemberRepository` 需要补：

- `Optional<GroupMember> findByApplicationId(Long applicationId)` 已存在，可直接复用
- `List<GroupMember> findAllByUserId(Long userId)` 已存在
- 可额外补 `List<GroupMember> findAllByApplicationIdIn(Collection<Long> ids)`，用于列表批量回填分组信息，避免 N+1

`RecruitmentGroupRepository` 可补：

- `List<RecruitmentGroup> findAllByIdIn(Collection<Long> ids)` 已存在，可复用

`DirectionRepository` 可复用现有：

- 管理模块里已经具备基础查询能力
- 报名模块需要补按 ID 批量查方向并组装名称映射

## 9. 业务规则落实方案

### 9.1 时期规则

- 创建、修改、撤回都必须调用 `PeriodService.ensureRegistrationOpen()`
- 查询列表、查询详情、查询 summary 不受时期限制

### 9.2 用户归属规则

- 所有用户侧报名接口只处理当前登录用户自己的数据
- `GET /api/v1/applications/{id}`、`PUT`、`DELETE` 都必须校验归属

### 9.3 方向规则

- `directionLevel1Id` 必须存在且是一级方向
- `directionLevel2Id` 必须存在且是二级方向
- 二级方向的 `parentId` 必须等于提交的一级方向 ID
- 建议默认只允许选择启用状态的方向

### 9.4 重复申请规则

- 同一用户同一 `directionLevel2Id` 只能有一条申请记录
- 新建时若已存在同方向申请，直接报冲突
- 修改时允许保留当前方向，但禁止改成与本人其他申请重复的方向

### 9.5 状态规则

- 新建默认 `SUBMITTED`
- 撤回后置为 `WITHDRAWN`
- 仅 `SUBMITTED` 状态允许修改和撤回
- `GROUPED`、`WITHDRAWN`、`REJECTED` 都不允许修改

### 9.6 分组联动规则

- 若某申请已存在 `group_member` 记录，则视为已分组
- 即使状态异常未同步，也应以“存在分组关系”为更强约束，禁止修改和撤回

### 9.7 年级规则

根据当前需求说明，本期默认只允许：

- `YEAR_1`
- `YEAR_2`

建议本轮先在服务层写死校验，报错信息明确为：

- “当前招新仅允许大一和大二报名”

后续如要改成可配置，再单独抽成配置项。

### 9.8 入学年份规则

建议校验：

- 必须为四位数
- 不早于 `currentYear - 6`
- 不晚于 `currentYear + 1`

说明：

- 这里只做基本数据清洗，避免明显脏数据
- 若你希望更严格按年级推导入学年份，可在正式实现前再定

## 10. 返回数据组装方案

为了让前端直接可用，报名返回对象建议带上方向名称和分组名称，而不是只返回 ID。

### 10.1 方向名称来源

- 通过 `DirectionRepository` 批量查询 `directionLevel1Id / directionLevel2Id`
- 组装 `directionLevel1Name / directionLevel2Name`

### 10.2 分组信息来源

- 通过 `GroupMember` 找到 `applicationId -> groupId`
- 再批量查 `RecruitmentGroup`
- 组装 `groupId / groupName`

### 10.3 性能要求

- 列表接口应避免按申请逐条查方向和分组
- 必须批量查询并在内存中映射

## 11. Controller 规划

建议新增：

- `controller/application/ApplicationController`

接口风格保持与现有项目一致：

- `@RestController`
- `@RequestMapping("/api/v1/applications")`
- 返回统一 `ApiResponse`
- 参数使用 `@Valid`

本轮不建议加复杂的 `@PreAuthorize` 表达式，原因是：

- 当前用户侧接口全部基于当前登录人，不存在跨用户访问入口
- 真正的归属限制放在 service 更直接

---

## 12. 异常与错误码策略

沿用现有异常体系。

建议使用：

- `NotFoundException`：申请不存在
- `ConflictException`：方向冲突、状态冲突、方向关系错误、年级不允许
- `PeriodNotAllowedException`：非报名期写操作
- `ForbiddenException`：访问他人申请

说明：

- 当前项目已有 `BusinessException` 分层，不需要再单独新建报名专用异常

## 13. 测试规划

### 13.1 单元测试

建议新增：

- `service/application/ApplicationServiceTest`

覆盖重点：

- 报名期允许创建
- 非报名期拒绝创建
- 一级二级方向不匹配拒绝
- 同方向重复申请拒绝
- 非 `YEAR_1 / YEAR_2` 拒绝
- 已分组申请不可修改
- 已撤回申请不可修改
- 撤回后状态更新为 `WITHDRAWN`
- 列表返回能正确带出方向和分组信息

### 13.2 集成测试

建议新增：

- `integration/ApplicationFlowIntegrationTest`

覆盖重点：

- 登录后创建申请成功
- 同方向重复提交返回冲突
- 修改自己申请成功
- 修改他人申请被拒绝
- 报名期关闭时写接口被拒绝
- 撤回后再修改被拒绝
- `summary` 统计正确

## 14. 数据库迁移判断

当前 `application` 表已经存在，字段基本够用，本轮原则上不需要新增迁移。

仅在以下场景才考虑新迁移：

- 需要补索引
- 需要补逻辑删除字段
- 需要补更严格约束

现阶段不建议为了报名模块再改表结构，优先把业务先跑通。

## 16. 需要你确认的关键边界

请重点确认以下几点：

1. 本轮是否只做“用户侧报名接口”，暂不做管理员报名管理
2. 返回对象是否需要直接带 `directionLevel1Name / directionLevel2Name / groupName`
3. 当前是否接受先把“仅允许 `YEAR_1 / YEAR_2` 报名”写死在服务层
4. 入学年份是否接受本轮只做基础范围校验，不做“按年级反推年份”的强规则

---

## 17. 结论

报名模块在当前代码基线上实现成本可控，因为认证、时期、方向、分组基础表都已经在位。  
最合适的实现策略是先做“用户侧报名闭环”，把提交、修改、撤回、查看和汇总一次接通，再继续推进管理端报名管理与分组模块。
