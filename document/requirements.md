## 1. 文档目标

本文档用于明确当前 `backend` 项目已经实现并保留的业务范围、角色权限、核心流程、数据约束和验收标准。
当前项目以代码实现为准；本文档同步当前实现细节，不描述尚未落地的理想扩展能力。

本文档解决以下问题：

- 统一“谁可以做什么”
- 统一“什么时间可以做什么”
- 统一“业务数据如何流转”
- 统一“哪些内容必须开发，哪些可以后置”

## 2. 项目概述

### 2.1 项目背景

实验室需要一套内部招新管理平台，覆盖报名、分组、任务考核、公告通知和资料发放等流程。  
平台同时服务三类角色：

- 新生
- 负责人
- 管理员

系统提供两类 Web 入口：

- 用户端：面向新生和负责人
- 管理端：面向管理员

### 2.2 项目目标

- 支持新生在线注册、登录、填写一份或多份报名申请，并进入多个不同分组学习
- 支持管理员配置招新时期、学习方向、分组和负责人
- 支持负责人发布组内任务、批阅提交、查看组员信息
- 支持公告和学习资料统一管理
- 支持基于角色、资源归属、时期状态的后端权限控制

### 2.3 非目标

以下内容不在本期范围内：

- 在线笔试系统
- 在线面试系统
- 即时聊天
- 多实验室多租户支持
- 移动端 App

## 3. 角色定义与权限边界

### 3.1 角色定义

| 角色 | 标识 | 说明 |
| --- | --- | --- |
| 新生 | `FRESHMAN` | 注册后的默认角色，可报名、查看公告资料、提交任务、查看成绩 |
| 负责人 | `LEADER` | 由管理员任命，负责一个分组的公告、任务和批阅 |
| 管理员 | `ADMIN` | 平台最高权限，管理全局配置和全部业务数据 |

### 3.2 权限模型

权限必须同时经过三层校验：

1. 角色权限：是否具备基础角色能力
2. 资源权限：该数据是否归当前用户可访问
3. 时期权限：当前业务时期是否允许该操作

### 3.3 权限矩阵

| 功能 | 新生 | 负责人 | 管理员 |
| --- | --- | --- | --- |
| 注册 | 仅报名期 | 仅报名期 | 不通过公开注册，后台初始化或人工导入 |
| 登录 | ✅ | ✅ | ✅ |
| 找回密码 | ✅ | ✅ | ✅ |
| 修改密码 | ✅ | ✅ | ✅ |
| 查看当前用户信息 | 仅本人 | 仅本人 | 仅本人 |
| 提交报名申请 | 仅本人，且仅报名期 | — | — |
| 修改/撤回报名申请 | 仅本人，且仅报名截止前 | — | 管理端可查看，不直接代填 |
| 查看公告 | 全局 + 所在组 | 全局 + 负责组 | 全部 |
| 发布公告 | — | 仅负责组 | 全局公告，可管理全部公告 |
| 查看学习资料 | 按权限可见 | 按权限可见 | 全部 |
| 发布学习资料 | — | 仅负责组 | 可管理任意组资料 |
| 查看任务 | 仅本人所属组任务 | 仅负责组任务 | 全部组任务 |
| 发布任务 | — | 仅负责组 | 可发布任意组任务 |
| 提交任务 | 当前所在组任务，且仅选拔期内截止前 | 当前所在组任务，且仅选拔期内截止前 | 当前所在组任务，且仅选拔期内截止前 |
| 批阅任务 | — | 仅负责组 | 全部 |
| 查看组员信息 | — | 仅负责组 | 全部 |
| 分组管理 | — | — | ✅ |
| 负责人任命/撤销 | — | — | ✅ |
| 学习方向管理 | — | — | ✅ |
| 招新时期管理 | — | — | ✅ |
| 数据看板/导出 | — | 仅负责组 | 全部 |

### 3.4 权限边界说明

- `LEADER` 不是“全局负责人”，只能操作自己负责的分组
- 负责人权限不能只靠角色判断，必须同时校验 `groupId` 归属
- 管理员可查看全部数据，但仍需经过后端鉴权
- 前端隐藏按钮不等于权限控制，后端必须拒绝越权请求

## 4. 招新时期定义

### 4.1 时期枚举

系统存在四个业务状态：

| 时期 | 标识 | 说明 |
| --- | --- | --- |
| 报名期 | `REGISTRATION` | 新生可注册、提交报名 |
| 选拔期 | `SELECTION` | 停止报名，进行分组、任务发布与任务提交 |
| 面试期 | `INTERVIEW` | 仅保留公告、资料和面试相关通知展示 |
| 已结束 | `FINISHED` | 由时间自动推导，不单独配置 |

### 4.2 时期规则

- 管理员配置 `REGISTRATION`、`SELECTION`、`INTERVIEW` 三个时期的起止时间
- `FINISHED` 由“当前时间晚于 `INTERVIEW.endTime`”自动推导
- 三个已配置时期不得重叠；即使某个时期被禁用，也不能与其他已配置时期重叠
- 若某时期未配置，则视为该时期未开放

### 4.3 时期与操作关系

| 操作 | 报名期 | 选拔期 | 面试期 | 已结束 |
| --- | --- | --- | --- | --- |
| 登录 | ✅ | ✅ | ✅ | ✅ |
| 找回密码/修改密码 | ✅ | ✅ | ✅ | ✅ |
| 注册 | ✅ | — | — | — |
| 提交/修改报名 | ✅ | — | — | — |
| 查看公告/资料 | ✅ | ✅ | ✅ | ✅ |
| 分组管理 | — | ✅ | 视运营需要，默认关闭 | — |
| 发布任务 | — | ✅ | — | — |
| 提交任务 | — | ✅ | — | — |
| 查看历史任务成绩 | — | ✅ | ✅ | ✅ |

### 4.4 关键澄清

- 登录不受时期限制，否则管理员和负责人无法在非报名期进入系统
- 注册只在报名期开放，管理员账号不走公开注册流程
- 修改报名仅允许在报名期且该申请尚未被分组前进行

## 5. 核心业务流程

### 5.1 用户注册流程

1. 用户输入邮箱，请求发送注册验证码
2. 系统校验邮箱格式和发送频率
3. 用户填写用户名、邮箱、密码、确认密码、验证码
4. 系统校验验证码、用户名唯一性、邮箱唯一性、密码强度
5. 创建用户，默认角色为 `FRESHMAN`
6. 注册成功后可直接登录

### 5.2 用户登录流程

1. 用户输入邮箱和密码
2. 系统校验账号存在、状态正常、密码正确
3. 生成登录态并写入 `HttpOnly Cookie`
4. 返回当前用户基础信息和角色信息

### 5.3 报名流程

1. 新生登录后进入报名页
2. 系统校验当前为报名期
3. 用户可为不同方向创建多份报名申请
4. 系统按申请维度保存报名信息并设置申请状态
5. 报名截止前允许本人修改或撤回未分组申请

### 5.4 分组流程

1. 管理员创建分组并设置方向、年级、入学年份、容量
2. 管理员或负责人在选拔期查看未分组申请列表
3. 管理员可将符合条件的申请加入任意匹配分组
4. 负责人可查看全局未分组申请列表，但只能把申请加入自己负责的分组
5. 系统按方向、年级、入学年份、容量规则校验分组
6. 当前没有自动分组接口，也没有拖拽接口；分组通过 HTTP 接口逐条分配
7. 管理员可把已存在的 `LEADER` 用户指派为分组负责人
8. 分组基础配置、负责人指派和移除可在选拔期前提前维护；申请分配、取消分组和拒绝申请必须处于选拔期

### 5.5 任务流程

1. 负责人或管理员在具体分组下发布任务
2. 新生在选拔期内查看自己所在组任务并提交
3. 每个任务对每名成员只保留一条当前提交记录
4. 未提交时状态为 `PENDING`，提交后为 `SUBMITTED`
5. 负责人或管理员批阅并打分，状态变为 `REVIEWED`
6. 如需重新提交，负责人或管理员先打回；打回会清空原提交内容、附件和评测信息，状态恢复为 `PENDING`
7. 新生查看当前提交状态、成绩和评语

## 6. 核心业务对象与状态流转

### 6.1 用户状态

| 状态 | 标识 | 说明 |
| --- | --- | --- |
| 正常 | `ACTIVE` | 可正常登录和使用 |
| 禁用 | `DISABLED` | 禁止登录和使用 |

### 6.2 报名申请状态

为避免实现歧义，申请记录状态统一如下：

| 状态 | 标识 | 说明 |
| --- | --- | --- |
| 已提交 | `SUBMITTED` | 已提交申请，等待分组 |
| 已分组 | `GROUPED` | 该申请已被选中并进入某个分组 |
| 已驳回 | `REJECTED` | 管理员或系统关闭该申请 |
| 已撤回 | `WITHDRAWN` | 用户在报名期主动撤回申请 |

说明：

- 本期不做草稿箱，因此不设置 `DRAFT`
- 报名申请一旦创建即视为正式提交
- 一个用户可同时拥有多条 `SUBMITTED` 状态申请
- 同一用户可有多条申请分别进入 `GROUPED`
- 每条申请的状态独立流转

### 6.3 任务提交状态

| 状态 | 标识 | 说明 |
| --- | --- | --- |
| 待提交 | `PENDING` | 当前任务暂无有效提交，或被打回后等待重新提交 |
| 已提交 | `SUBMITTED` | 存在有效提交 |
| 已批阅 | `REVIEWED` | 当前提交已评分 |

说明：

- 当前实现不单独持久化 `EXPIRED` 状态，是否截止由任务 `deadlineAt` 动态判断。
- 当前实现不保留多次提交历史，同一任务同一用户只有一条 `task_submission` 记录。

### 6.4 公告可见范围

| 范围 | 标识 | 说明 |
| --- | --- | --- |
| 全局公告 | `GLOBAL` | 所有人可见 |
| 组内公告 | `GROUP` | 对应分组成员、该组负责人和管理员可见 |

### 6.5 任务范围

当前任务只支持组内任务：

| 范围 | 说明 |
| --- | --- |
| 组内任务 | 每个任务必须绑定一个分组，仅对应分组成员、该组负责人和管理员可见 |

## 7. 功能需求

### 7.1 认证与账号模块

#### 7.1.1 注册

- 使用邮箱注册
- 注册字段：
  - 用户名
  - 邮箱
  - 密码
  - 确认密码
  - 邮箱验证码
- 用户名全局唯一
- 邮箱全局唯一
- 密码长度至少 8 位，必须同时包含字母和数字
- 注册成功后默认角色为 `FRESHMAN`

#### 7.1.2 登录

- 使用邮箱 + 密码登录
- 支持“记住我”
- 登录成功后返回当前用户基础信息
- 前端根据角色跳转：
  - 新生：用户端首页
  - 负责人：用户端首页，带负责人功能入口
  - 管理员：管理端首页

#### 7.1.3 找回密码

- 通过邮箱验证码找回
- 流程：
  - 输入邮箱
  - 发送找回验证码
  - 输入新密码、确认密码、验证码
  - 系统校验后更新密码

#### 7.1.4 修改密码

- 仅登录用户可用
- 必须校验旧密码
- 修改成功后旧登录态失效，需重新登录

### 7.2 报名模块

#### 7.2.1 报名申请字段

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| 真实姓名 | 字符串 | 必填，1 到 32 字 |
| 手机号 | 字符串 | 必填，校验大陆手机号格式 |
| 学院 | 字符串 | 必填，1 到 64 字 |
| 专业 | 字符串 | 必填，1 到 64 字 |
| 班级 | 字符串 | 必填，1 到 64 字 |
| 年级 | 枚举 | 必填，`YEAR_1 / YEAR_2 / YEAR_3 / YEAR_4 / GRADUATED` |
| 入学年份 | 整数 | 必填，四位年份，如 `2026` |
| 一级方向 ID | Long | 必填，必须存在 |
| 二级方向 ID | Long | 必填，必须属于所选一级方向 |
| 自我介绍 | 文本 | 可选，最多 1000 字 |

#### 7.2.2 报名申请规则

- 仅报名期可提交
- 一个用户可提交多份不同方向的报名申请
- “不同方向”定义为 `directionLevel2Id` 不同；同一方向重复申请应视为修改原申请，而不是新增
- 报名截止前允许本人修改或撤回尚未分组的申请
- 已进入分组的申请不可修改或撤回
- 管理员可查看全部申请，但本期不开放管理员代填
- 系统层面支持记录 `YEAR_1 / YEAR_2 / YEAR_3 / YEAR_4 / GRADUATED`
- 当前招新业务默认仅允许 `YEAR_1` 和 `YEAR_2` 报名，若未来放开高年级，需要同步调整业务规则与前端提示

### 7.3 学习方向模块

#### 7.3.1 方向结构

- 仅支持两级结构
- 一级方向示例：后端、前端、算法、产品
- 二级方向示例：Java、Go、Vue、React

#### 7.3.2 管理规则

- 一级方向下可有多个二级方向
- 二级方向必须从属于某个一级方向
- 删除方向前必须校验：
  - 无报名使用
  - 无分组绑定
  - 无资料绑定

### 7.4 分组模块

#### 7.4.1 分组字段

| 字段 | 说明 |
| --- | --- |
| 分组名称 | 必填，全局唯一 |
| 一级方向 ID | 必填 |
| 二级方向 ID | 必填 |
| 年级 | 必填 |
| 入学年份 | 必填，四位年份 |
| 最大人数 | 必填，范围 1 到 200 |
| 负责人用户 ID | 可空，指派后填写 |

#### 7.4.2 当前分组规则

当前没有自动分组接口。管理员或负责人通过 HTTP 接口逐条分配申请时必须满足：

1. 分组以“报名申请”为候选单元，而不是以“用户”为候选单元
2. 同一组内成员年级一致
3. 同一组内成员入学年份一致
4. 同一组内成员方向一致
5. 不得超过组容量
6. 同一用户可因不同申请进入多个不同分组
7. 同一申请最多只能被分配到一个分组
8. 无法匹配的申请保留在未分配列表

#### 7.4.3 当前分组调整规则

- 管理员可操作任意分组。
- 负责人可操作自己负责的分组。
- 创建、修改、删除空分组、指派负责人和移除负责人不受招新时期限制，可提前维护。
- 加入目标组、取消分组和拒绝申请前必须校验方向、年级、入学年份、容量和时期。
- 同一申请最多只能存在一个分组关系。
- 当前没有直接“移动到另一组”接口；需要先取消原分组，再加入新分组。
- 取消分组会删除 `group_member` 关系，并把申请状态恢复为 `SUBMITTED`。
- 当前取消分组不会自动处理该用户是否为负责人；删除非空分组被禁止。

#### 7.4.4 负责人任命规则

- 一个组只能有一个负责人。
- 被指派用户必须已经是 `LEADER` 且状态为 `ACTIVE`。
- 当前指派负责人不会自动修改用户角色；如候选用户仍是 `FRESHMAN`，管理员需要先通过用户角色接口将其提升为 `LEADER`。
- 当前实现不强制负责人必须是该组成员。
- 当前实现不限制同一 `LEADER` 用户只能负责一个组。
- 撤销负责人只会清空分组的 `leaderUserId`，不会自动把用户角色降回 `FRESHMAN`；如需降级，管理员需要通过用户角色接口执行，且目标用户不能仍绑定任何负责的分组。

### 7.5 公告模块

#### 7.5.1 公告字段

| 字段 | 说明 |
| --- | --- |
| 标题 | 必填，1 到 100 字 |
| 内容 | 必填，Markdown，最多 20000 字 |
| 范围 | `GLOBAL` 或 `GROUP` |
| 组 ID | 组内公告必填，全局公告为空 |

#### 7.5.2 公告规则

- 管理员可管理全部公告
- 负责人只能管理自己负责组的公告
- Markdown 渲染必须做 XSS 过滤
- 列表默认按发布时间倒序

### 7.6 学习资料模块

#### 7.6.1 资料形式

- Markdown 文本
- 附件
- Markdown + 附件组合

#### 7.6.2 资料字段

| 字段 | 说明 |
| --- | --- |
| 标题 | 必填 |
| Markdown 内容 | 可空 |
| 附件文件 ID | 可空 |
| 分组 ID | 必填 |
| 发布者 ID | 系统写入 |

#### 7.6.3 可见规则

- 当前资料属于具体分组，不存在公开资料或按方向资料。
- 管理员可见全部资料。
- 负责人可见并管理自己负责组资料。
- 普通用户只能查看自己所在组资料。

### 7.7 任务模块

#### 7.7.1 任务字段

| 字段 | 说明 |
| --- | --- |
| 标题 | 必填，1 到 100 字 |
| 内容 | 必填，Markdown |
| 组 ID | 必填 |
| 截止时间 | 必填，必须晚于发布时间 |
| 满分 | 必填，1 到 100 |
| 附件文件 ID | 可空 |

#### 7.7.2 提交规则

- 仅选拔期可提交
- 仅任务所在组当前成员可提交；权限来自组成员身份，不来自管理员或负责人身份
- 截止时间后不可提交
- 同一任务同一用户只有一条当前提交记录
- 提交状态为 `PENDING` 时才允许提交
- 已提交或已批阅后不能直接覆盖；需要负责人或管理员先打回
- 打回会清空当前提交正文、附件、提交时间、评测人、分数、评语和评测时间

#### 7.7.3 批阅规则

- 负责人只能批阅自己负责组的组任务提交
- 管理员可批阅全部
- 分数必须在 `0` 到 `maxScore` 之间
- 批阅后仍允许重复批阅，以最后一次结果为准，并保留批阅更新时间

### 7.8 数据看板与导出

管理员可查看全局数据看板，负责人可查看自己负责组的数据看板。看板包括：

- 注册人数
- 已提交申请数
- 已报名用户数
- 已分组人数
- 已分组申请数
- 未分配人数
- 各组人数
- 任务完成率
- 成绩汇总

管理员可导出全局或任意组数据，负责人可导出自己负责组数据。可导出内容包括：

- 报名信息（仅管理员全局导出）
- 分组结果
- 任务成绩

导出格式本期统一为 Excel

## 11. 验收标准

### 11.1 认证模块验收

- 可以完成注册、登录、退出登录、找回密码、修改密码
- 未登录访问受保护接口返回 401
- 无权限访问返回 403
- 修改密码后旧登录态失效

### 11.2 报名模块验收

- 报名期可提交、修改和撤回申请
- 非报名期提交申请被拒绝
- 同一用户可创建多份不同方向申请，但同一方向不能重复新增
- 同一用户可有多份不同申请分别进入不同分组
- 申请列表可正确显示状态、方向和分组结果

### 11.3 分组模块验收

- 管理员可创建、修改、删除空分组
- 分组分配遵守方向、年级、入学年份、容量规则
- 不符合条件的申请保留在未分配列表
- 负责人只能把申请加入自己负责的分组
- 负责人账号必须是 `LEADER` 且 `ACTIVE`；管理员可先通过用户角色接口将 `FRESHMAN` 提升为 `LEADER`

### 11.4 任务模块验收

- 仅选拔期可提交任务
- 超过截止时间后不可提交
- 当前状态为 `PENDING` 时可提交
- 已提交或已批阅后需先由负责人或管理员打回再重交
- 评分不能超过满分

### 11.5 权限模块验收

- 负责人不能查看或操作非自己负责组的数据
- 新生不能访问管理端接口
- 管理员可查看并管理全局数据

## 12. 开发前必须确认的固定决策

以下决策在本文件中已经固定，开发时不再重复讨论：

- 登录始终允许，注册仅报名期允许
- 申请状态使用 `SUBMITTED / GROUPED / REJECTED / WITHDRAWN`
- 同一用户可提交多份不同方向申请，并可因不同申请进入多个不同分组
- 负责人任命不会同步修改用户角色；候选用户必须已经是 `LEADER` 且 `ACTIVE`，角色提升或降级由管理员用户角色接口显式完成
- 负责人权限必须叠加组归属校验
- 负责人可查看全局未分组申请列表，但只能操作自己负责的分组
- 任务每名成员只保留一条当前提交记录；重新提交依赖打回流程
- 任务和学习资料均为组级资源，不支持全局任务或公开资料
- 导出格式本期统一为 Excel
