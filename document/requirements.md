## 1. 文档目标

本文档用于明确实验室招新平台的业务范围、角色权限、核心流程、数据约束和验收标准。  
开发、接口设计、数据库设计、测试用例和前端页面实现均以本文件为业务基线。

本文档解决以下问题：

- 统一“谁可以做什么”
- 统一“什么时间可以做什么”
- 统一“业务数据如何流转”
- 统一“哪些内容必须开发，哪些可以后置”

## 2. 项目概述

### 2.1 项目背景

实验室需要一套内部招新管理平台，覆盖报名、分组、任务考核、公告通知和资料发放等流程。  
平台同时服务三类角色：

- 新生
- 负责人
- 管理员

系统提供两类 Web 入口：

- 用户端：面向新生和负责人
- 管理端：面向管理员

### 2.2 项目目标

- 支持新生在线注册、登录、填写一份或多份报名申请，并进入多个不同分组学习
- 支持管理员配置招新时期、学习方向、分组和负责人
- 支持负责人发布组内任务、批阅提交、查看组员信息
- 支持公告和学习资料统一管理
- 支持基于角色、资源归属、时期状态的后端权限控制

### 2.3 非目标

以下内容不在本期范围内：

- 在线笔试系统
- 在线面试系统
- 即时聊天
- 多实验室多租户支持
- 移动端 App

## 3. 角色定义与权限边界

### 3.1 角色定义

| 角色 | 标识 | 说明 |
| --- | --- | --- |
| 新生 | `FRESHMAN` | 注册后的默认角色，可报名、查看公告资料、提交任务、查看成绩 |
| 负责人 | `LEADER` | 由管理员任命，负责一个分组的公告、任务和批阅 |
| 管理员 | `ADMIN` | 平台最高权限，管理全局配置和全部业务数据 |

### 3.2 权限模型

权限必须同时经过三层校验：

1. 角色权限：是否具备基础角色能力
2. 资源权限：该数据是否归当前用户可访问
3. 时期权限：当前业务时期是否允许该操作

### 3.3 权限矩阵

| 功能 | 新生 | 负责人 | 管理员 |
| --- | --- | --- | --- |
| 注册 | 仅报名期 | 仅报名期 | 不通过公开注册，后台初始化或人工导入 |
| 登录 | ✅ | ✅ | ✅ |
| 找回密码 | ✅ | ✅ | ✅ |
| 修改密码 | ✅ | ✅ | ✅ |
| 查看当前用户信息 | 仅本人 | 仅本人 | 仅本人 |
| 提交报名申请 | 仅本人，且仅报名期 | — | — |
| 修改/撤回报名申请 | 仅本人，且仅报名截止前 | — | 管理端可查看，不直接代填 |
| 查看公告 | 全局 + 所在组 | 全局 + 负责组 | 全部 |
| 发布公告 | — | 仅负责组 | 全局公告，可管理全部公告 |
| 查看学习资料 | 按权限可见 | 按权限可见 | 全部 |
| 发布学习资料 | — | — | ✅ |
| 查看任务 | 仅本人所属各组及全局任务 | 仅负责组及全局任务 | 全部 |
| 发布任务 | — | 仅负责组 | 可发布全局任务或指定组任务 |
| 提交任务 | 仅本人，且仅选拔期内截止前 | — | — |
| 批阅任务 | — | 仅负责组 | 全部 |
| 查看组员信息 | — | 仅负责组 | 全部 |
| 分组管理 | — | — | ✅ |
| 负责人任命/撤销 | — | — | ✅ |
| 学习方向管理 | — | — | ✅ |
| 招新时期管理 | — | — | ✅ |
| 数据看板/导出 | — | — | ✅ |

### 3.4 权限边界说明

- `LEADER` 不是“全局负责人”，只能操作自己负责的分组
- 负责人权限不能只靠角色判断，必须同时校验 `groupId` 归属
- 管理员可查看全部数据，但仍需经过后端鉴权
- 前端隐藏按钮不等于权限控制，后端必须拒绝越权请求

## 4. 招新时期定义

### 4.1 时期枚举

系统存在四个业务状态：

| 时期 | 标识 | 说明 |
| --- | --- | --- |
| 报名期 | `REGISTRATION` | 新生可注册、提交报名 |
| 选拔期 | `SELECTION` | 停止报名，进行分组、任务发布与任务提交 |
| 面试期 | `INTERVIEW` | 仅保留公告、资料和面试相关通知展示 |
| 已结束 | `FINISHED` | 由时间自动推导，不单独配置 |

### 4.2 时期规则

- 管理员配置 `REGISTRATION`、`SELECTION`、`INTERVIEW` 三个时期的起止时间
- `FINISHED` 由“当前时间晚于 `INTERVIEW.endTime`”自动推导
- 三个已配置时期不得重叠
- 若某时期未配置，则视为该时期未开放

### 4.3 时期与操作关系

| 操作 | 报名期 | 选拔期 | 面试期 | 已结束 |
| --- | --- | --- | --- | --- |
| 登录 | ✅ | ✅ | ✅ | ✅ |
| 找回密码/修改密码 | ✅ | ✅ | ✅ | ✅ |
| 注册 | ✅ | — | — | — |
| 提交/修改报名 | ✅ | — | — | — |
| 查看公告/资料 | ✅ | ✅ | ✅ | ✅ |
| 分组管理 | — | ✅ | 视运营需要，默认关闭 | — |
| 发布任务 | — | ✅ | — | — |
| 提交任务 | — | ✅ | — | — |
| 查看历史任务成绩 | — | ✅ | ✅ | ✅ |

### 4.4 关键澄清

- 登录不受时期限制，否则管理员和负责人无法在非报名期进入系统
- 注册只在报名期开放，管理员账号不走公开注册流程
- 修改报名仅允许在报名期且该申请尚未被分组前进行

## 5. 核心业务流程

### 5.1 用户注册流程

1. 用户输入邮箱，请求发送注册验证码
2. 系统校验邮箱格式和发送频率
3. 用户填写用户名、邮箱、密码、确认密码、验证码
4. 系统校验验证码、用户名唯一性、邮箱唯一性、密码强度
5. 创建用户，默认角色为 `FRESHMAN`
6. 注册成功后可直接登录

### 5.2 用户登录流程

1. 用户输入邮箱和密码
2. 系统校验账号存在、状态正常、密码正确
3. 生成登录态并写入 `HttpOnly Cookie`
4. 返回当前用户基础信息和角色信息

### 5.3 报名流程

1. 新生登录后进入报名页
2. 系统校验当前为报名期
3. 用户可为不同方向创建多份报名申请
4. 系统按申请维度保存报名信息并设置申请状态
5. 报名截止前允许本人修改或撤回未分组申请

### 5.4 分组流程

1. 管理员创建分组并设置方向、年级、入学年份、容量
2. 管理员在选拔期触发自动分组
3. 系统按方向、年级、入学年份、容量规则尝试分配
4. 无法分配的申请进入未分配列表
5. 管理员可手动拖拽调整
6. 管理员任命组内一名成员为负责人

### 5.5 任务流程

1. 负责人或管理员发布任务
2. 新生在选拔期内查看任务并提交
3. 每个任务允许多次提交，以最后一次有效提交作为当前版本
4. 负责人或管理员批阅并打分
5. 新生查看成绩和评语

## 6. 核心业务对象与状态流转

### 6.1 用户状态

| 状态 | 标识 | 说明 |
| --- | --- | --- |
| 正常 | `ACTIVE` | 可正常登录和使用 |
| 禁用 | `DISABLED` | 禁止登录和使用 |

### 6.2 报名申请状态

为避免实现歧义，申请记录状态统一如下：

| 状态 | 标识 | 说明 |
| --- | --- | --- |
| 已提交 | `SUBMITTED` | 已提交申请，等待分组 |
| 已分组 | `GROUPED` | 该申请已被选中并进入某个分组 |
| 已驳回 | `REJECTED` | 管理员或系统关闭该申请 |
| 已撤回 | `WITHDRAWN` | 用户在报名期主动撤回申请 |

说明：

- 本期不做草稿箱，因此不设置 `DRAFT`
- 报名申请一旦创建即视为正式提交
- 一个用户可同时拥有多条 `SUBMITTED` 状态申请
- 同一用户可有多条申请分别进入 `GROUPED`
- 每条申请的状态独立流转

### 6.3 任务提交状态

| 状态 | 标识 | 说明 |
| --- | --- | --- |
| 未提交 | `NOT_SUBMITTED` | 当前任务暂无提交 |
| 已提交 | `SUBMITTED` | 存在有效提交 |
| 已截止 | `EXPIRED` | 超过截止时间且无新提交 |
| 已批阅 | `REVIEWED` | 最新有效提交已评分 |

### 6.4 公告可见范围

| 范围 | 标识 | 说明 |
| --- | --- | --- |
| 全局公告 | `GLOBAL` | 所有人可见 |
| 组内公告 | `GROUP` | 仅对应分组成员和管理员可见 |

### 6.5 任务范围

| 范围 | 标识 | 说明 |
| --- | --- | --- |
| 全局任务 | `GLOBAL` | 所有符合条件用户可见 |
| 组内任务 | `GROUP` | 仅对应分组成员可见 |

## 7. 功能需求

### 7.1 认证与账号模块

#### 7.1.1 注册

- 使用邮箱注册
- 注册字段：
  - 用户名
  - 邮箱
  - 密码
  - 确认密码
  - 邮箱验证码
- 用户名全局唯一
- 邮箱全局唯一
- 密码长度至少 8 位，必须同时包含字母和数字
- 注册成功后默认角色为 `FRESHMAN`

#### 7.1.2 登录

- 使用邮箱 + 密码登录
- 支持“记住我”
- 登录成功后返回当前用户基础信息
- 前端根据角色跳转：
  - 新生：用户端首页
  - 负责人：用户端首页，带负责人功能入口
  - 管理员：管理端首页

#### 7.1.3 找回密码

- 通过邮箱验证码找回
- 流程：
  - 输入邮箱
  - 发送找回验证码
  - 输入新密码、确认密码、验证码
  - 系统校验后更新密码

#### 7.1.4 修改密码

- 仅登录用户可用
- 必须校验旧密码
- 修改成功后旧登录态失效，需重新登录

### 7.2 报名模块

#### 7.2.1 报名申请字段

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| 真实姓名 | 字符串 | 必填，1 到 32 字 |
| 手机号 | 字符串 | 必填，校验大陆手机号格式 |
| 学院 | 字符串 | 必填，1 到 64 字 |
| 专业 | 字符串 | 必填，1 到 64 字 |
| 班级 | 字符串 | 必填，1 到 64 字 |
| 年级 | 枚举 | 必填，`YEAR_1 / YEAR_2 / YEAR_3 / YEAR_4 / GRADUATED` |
| 入学年份 | 整数 | 必填，四位年份，如 `2026` |
| 一级方向 ID | Long | 必填，必须存在 |
| 二级方向 ID | Long | 必填，必须属于所选一级方向 |
| 自我介绍 | 文本 | 可选，最多 1000 字 |

#### 7.2.2 报名申请规则

- 仅报名期可提交
- 一个用户可提交多份不同方向的报名申请
- “不同方向”定义为 `directionLevel2Id` 不同；同一方向重复申请应视为修改原申请，而不是新增
- 报名截止前允许本人修改或撤回尚未分组的申请
- 已进入分组的申请不可修改或撤回
- 管理员可查看全部申请，但本期不开放管理员代填
- 系统层面支持记录 `YEAR_1 / YEAR_2 / YEAR_3 / YEAR_4 / GRADUATED`
- 当前招新业务默认仅允许 `YEAR_1` 和 `YEAR_2` 报名，若未来放开高年级，需要同步调整业务规则与前端提示

### 7.3 学习方向模块

#### 7.3.1 方向结构

- 仅支持两级结构
- 一级方向示例：后端、前端、算法、产品
- 二级方向示例：Java、Go、Vue、React

#### 7.3.2 管理规则

- 一级方向下可有多个二级方向
- 二级方向必须从属于某个一级方向
- 删除方向前必须校验：
  - 无报名使用
  - 无分组绑定
  - 无资料绑定

### 7.4 分组模块

#### 7.4.1 分组字段

| 字段 | 说明 |
| --- | --- |
| 分组名称 | 必填，全局唯一 |
| 一级方向 ID | 必填 |
| 二级方向 ID | 必填 |
| 年级 | 必填 |
| 入学年份 | 必填，四位年份 |
| 最大人数 | 必填，范围 1 到 200 |
| 负责人用户 ID | 可空，任命后填写 |

#### 7.4.2 自动分组规则

自动分组时必须满足：

1. 分组以“报名申请”为候选单元，而不是以“用户”为候选单元
2. 同一组内成员年级一致
3. 同一组内成员入学年份一致
4. 同一组内成员方向一致
5. 不得超过组容量
6. 同一用户可因不同申请进入多个不同分组
7. 同一申请最多只能被分配到一个分组
8. 无法匹配的申请进入未分配列表

#### 7.4.3 手动调整规则

- 仅管理员可手动调整
- 拖入目标组前必须校验方向、年级、入学年份、容量
- 同一申请若已被分配到某组，则移动时应先移除旧组关系再加入新组
- 用户被移动到新组后，旧组关系自动移除
- 若该用户是旧组负责人，移动前必须先撤销负责人身份

#### 7.4.4 负责人任命规则

- 负责人必须是该组成员
- 一个组只能有一个负责人
- 一个用户在本期只能负责一个组
- 任命后用户角色更新为 `LEADER`
- 若撤销后用户不再负责任何组，则角色降回 `FRESHMAN`

### 7.5 公告模块

#### 7.5.1 公告字段

| 字段 | 说明 |
| --- | --- |
| 标题 | 必填，1 到 100 字 |
| 内容 | 必填，Markdown，最多 20000 字 |
| 范围 | `GLOBAL` 或 `GROUP` |
| 组 ID | 组内公告必填，全局公告为空 |
| 发布者 ID | 系统写入 |
| 发布时间 | 系统写入 |

#### 7.5.2 公告规则

- 管理员可管理全部公告
- 负责人只能管理自己负责组的公告
- Markdown 渲染必须做 XSS 过滤
- 列表默认按发布时间倒序

### 7.6 学习资料模块

#### 7.6.1 资料形式

- Markdown 文本
- 附件
- Markdown + 附件组合

#### 7.6.2 资料字段

| 字段 | 说明 |
| --- | --- |
| 标题 | 必填 |
| 摘要 | 可选，最多 300 字 |
| Markdown 内容 | 可空 |
| 附件地址 | 可空 |
| 一级方向 ID | 可空 |
| 二级方向 ID | 可空 |
| 发布者 ID | 系统写入 |

#### 7.6.3 可见规则

- 未绑定方向的资料视为公开资料
- 绑定方向的资料默认对所有登录用户可见，本期不做按方向强限制

### 7.7 任务模块

#### 7.7.1 任务字段

| 字段 | 说明 |
| --- | --- |
| 标题 | 必填，1 到 100 字 |
| 内容 | 必填，Markdown |
| 范围 | `GLOBAL` 或 `GROUP` |
| 组 ID | 组任务必填 |
| 截止时间 | 必填，必须晚于发布时间 |
| 满分 | 必填，1 到 100 |
| 附件地址 | 可空 |

#### 7.7.2 提交规则

- 仅选拔期可提交
- 仅任务可见用户可提交
- 截止时间后不可新增或覆盖提交
- 允许多次提交，以最后一次为准
- 历史提交记录保留，当前有效提交由系统标记

#### 7.7.3 批阅规则

- 负责人只能批阅自己负责组的组任务提交
- 管理员可批阅全部
- 分数必须在 `0` 到 `maxScore` 之间
- 批阅后仍允许重复批阅，以最后一次结果为准，并保留批阅更新时间

### 7.8 数据看板与导出

管理员可查看：

- 注册人数
- 已提交申请数
- 已报名用户数
- 已分组人数
- 已分组申请数
- 未分配人数
- 各组人数
- 任务完成率
- 成绩汇总

管理员可导出：

- 报名信息
- 分组结果
- 任务成绩

导出格式本期统一为 Excel

```text
  - id, title, content_markdown, scope, group_id, publisher_id, created_at, updated_at

Material
  - id, title, summary, content_markdown, attachment_url, direction_level1_id, direction_level2_id, publisher_id, created_at, updated_at

Task
  - id, title, content_markdown, scope, group_id, attachment_url, max_score, deadline_at, publisher_id, created_at, updated_at

TaskReview

```

### 9.2 关键约束

- `user.email` 唯一
- `user.username` 唯一
- `application(user_id, direction_level2_id)` 唯一
- `group_member(user_id, group_id)` 唯一
- `group_member.application_id` 唯一
- `recruitment_group.name` 唯一
- `task_submission` 允许多条，但同一任务同一用户只能有一条 `is_latest=true`

## 10. 非功能性需求

### 10.1 性能

- 首屏加载时间目标小于 3 秒
- 普通列表接口响应时间目标小于 500ms
- 分页接口单页最大 50 条

### 10.2 安全

- 密码必须加密存储
- 登录态必须防止 XSS 窃取
- 文件上传必须校验类型和大小
- Markdown 渲染必须进行 XSS 过滤
- 所有写操作接口必须做鉴权和参数校验

### 10.3 可维护性

- 后端接口统一返回结构
- 错误码统一管理
- 关键写操作保留审计日志
- 数据库结构通过迁移脚本管理

### 10.4 可用性

- 表单错误必须返回明确字段级提示
- 删除、撤销任命、时期调整等关键操作需二次确认
- 上传失败、权限不足、时期不允许等场景必须给出明确错误信息

## 11. 验收标准

### 11.1 认证模块验收

- 可以完成注册、登录、退出登录、找回密码、修改密码
- 未登录访问受保护接口返回 401
- 无权限访问返回 403
- 修改密码后旧登录态失效

### 11.2 报名模块验收

- 报名期可提交、修改和撤回申请
- 非报名期提交申请被拒绝
- 同一用户可创建多份不同方向申请，但同一方向不能重复新增
- 同一用户可有多份不同申请分别进入不同分组
- 申请列表可正确显示状态、方向和分组结果

### 11.3 分组模块验收

- 自动分组遵守方向、年级、入学年份、容量规则
- 不符合条件的用户进入未分配列表
- 手动拖拽不允许越过规则限制

### 11.4 任务模块验收

- 仅选拔期可提交任务
- 超过截止时间后不可提交
- 多次提交后仅最新版本生效
- 评分不能超过满分

### 11.5 权限模块验收

- 负责人不能查看或操作非自己负责组的数据
- 新生不能访问管理端接口
- 管理员可查看并管理全局数据

## 12. 开发前必须确认的固定决策

以下决策在本文件中已经固定，开发时不再重复讨论：

- 登录始终允许，注册仅报名期允许
- 申请状态使用 `SUBMITTED / GROUPED / REJECTED / WITHDRAWN`
- 同一用户可提交多份不同方向申请，并可因不同申请进入多个不同分组
- 负责人任命会同步修改用户角色为 `LEADER`
- 负责人权限必须叠加组归属校验
- 任务支持多次提交，最后一次为当前有效版本
- 导出格式本期统一为 Excel
