# 用户登录注册与权限控制实现指导

> 版本：v2.0
> 日期：2026-06-24
> 适用范围：后端 Spring Boot 实现
> 依赖文档：`requirements.md`、`API需求文档与技术栈选型.md`

---

## 1. 文档目标

本文档不是概念说明，而是后端开发落地手册。  
目标是让开发者按本文档即可直接实现：

- 注册
- 登录
- 退出登录
- 获取当前用户信息
- 找回密码
- 修改密码
- 基于角色、资源归属、时期状态的权限控制

实现完成后，报名、分组、公告、资料、任务模块应能复用同一套鉴权基础设施。

---

## 2. 本文固定决策

这些点在开发时不再讨论，直接按此执行：

1. 登录态方案：`JWT + HttpOnly Cookie`
2. 后端权限判断分三层：角色、资源归属、时期
3. 登录不受时期限制，注册仅报名期开放
4. 负责人必须同时满足：
   - 用户角色为 `LEADER`
   - 操作的资源属于其负责组
5. 修改密码和重置密码都会让旧 Token 失效
6. Redis 用于验证码、黑名单、限流和失败计数
7. 统一异常响应，不在 Controller 里手写零散 `if-else`

## 3. 模块目标与边界

### 3.1 该模块负责什么

- 身份认证
- 登录态维护
- 基础角色鉴权
- 资源级权限表达式
- 时期级权限表达式
- 认证相关限流

### 3.2 该模块不负责什么

- 业务表单渲染
- 公告、任务、分组的具体业务逻辑
- 文件上传实现细节

说明：

- 这些业务模块只需要复用认证与权限组件，不要在它们内部重复造鉴权逻辑

## 6. 领域模型设计

## 6.1 `User`

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Long | 主键 |
| `username` | String | 唯一 |
| `email` | String | 唯一 |
| `passwordHash` | String | BCrypt 哈希 |
| `role` | Enum | `FRESHMAN` / `LEADER` / `ADMIN` |
| `status` | Enum | `ACTIVE` / `DISABLED` |
| `emailVerified` | Boolean | 邮箱是否已验证 |
| `tokenVersion` | Long | Token 版本号 |
| `lastLoginAt` | LocalDateTime | 最后登录时间 |
| `createdAt` | LocalDateTime | 创建时间 |
| `updatedAt` | LocalDateTime | 更新时间 |

关键约束：

- `username` 唯一索引
- `email` 唯一索引
- `tokenVersion` 默认 `0`

## 6.2 `Application`

认证模块会读取报名信息判断资源归属和状态，建议同步建好：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Long | 主键 |
| `userId` | Long | 关联用户 |
| `realName` | String | 真实姓名 |
| `phone` | String | 手机号 |
| `college` | String | 学院 |
| `major` | String | 专业 |
| `className` | String | 班级 |
| `grade` | Enum | 年级 |
| `admissionYear` | Integer | 入学年份，如 `2026` |
| `directionLevel1Id` | Long | 一级方向 |
| `directionLevel2Id` | Long | 二级方向 |
| `introduction` | String | 自我介绍 |
| `status` | Enum | `SUBMITTED` / `GROUPED` / `REJECTED` / `WITHDRAWN` |
| `statusRemark` | String | 状态备注，可空 |
| `createdAt` | LocalDateTime | 创建时间 |
| `updatedAt` | LocalDateTime | 更新时间 |

实现约束：

- `admissionYear` 使用四位整数，例如 `2026`
- `grade` 负责表示当前年级阶段，`admissionYear` 负责表示哪一年入学
- 当前招新业务若仍只面向低年级，报名校验应默认只接受 `YEAR_1` 和 `YEAR_2`
- 一个用户可存在多条申请记录
- 同一用户对同一 `directionLevel2Id` 只允许存在一条申请记录
- 同一申请最多只能进入一个分组

## 6.3 `RecruitmentGroup`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Long | 主键 |

| 字段 | 类型 | 说明 |

## 11. SecurityConfig 实现要求

`SecurityConfig` 是整个链路的装配中心，必须完成以下配置：

### 11.1 必配 Bean

- `PasswordEncoder`
- `AuthenticationManager`
- `DaoAuthenticationProvider`
- `SecurityFilterChain`
- `AuthenticationEntryPoint`
- `AccessDeniedHandler`

### 11.2 SecurityFilterChain 要求

必须做到：

1. 关闭默认表单登录
2. 关闭 HTTP Basic
3. 使用无状态会话
4. 加入 `JwtAuthenticationFilter`
5. 放行以下接口：
   - `/api/v1/auth/login`
   - `/api/v1/auth/register`
   - `/api/v1/auth/send-email-code`
   - `/api/v1/auth/forgot-password`
   - `/api/v1/auth/reset-password`
   - `/api/v1/meta/current-period`
   - `/api/v1/directions`
6. 放行静态资源和前端入口
7. `/api/v1/admin/**` 要求 `ADMIN`
8. `/api/v1/leader/**` 要求 `LEADER` 或 `ADMIN`
9. 其他 `/api/v1/**` 需要认证
10. 启用方法级权限 `@EnableMethodSecurity`

### 11.3 配置示意

```java
http
    .csrf(AbstractHttpConfigurer::disable)
    .formLogin(AbstractHttpConfigurer::disable)
    .httpBasic(AbstractHttpConfigurer::disable)
    .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .exceptionHandling(ex -> ex
        .authenticationEntryPoint(restAuthenticationEntryPoint)
        .accessDeniedHandler(restAccessDeniedHandler))
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/v1/auth/login", "/api/v1/auth/register").permitAll()
        .requestMatchers("/api/v1/auth/send-email-code", "/api/v1/auth/forgot-password", "/api/v1/auth/reset-password").permitAll()
        .requestMatchers("/api/v1/meta/current-period", "/api/v1/directions").permitAll()
        .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
        .requestMatchers("/api/v1/leader/**").hasAnyRole("LEADER", "ADMIN")
        .requestMatchers("/api/v1/**").authenticated()
        .anyRequest().permitAll())
    .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);
```

说明：

- 最终写法按当前 Spring Security 版本语法微调
- 但职责划分和顺序必须保持一致

## 12. JWT 设计

## 12.1 Claims 设计

JWT 建议包含：

| Claim | 说明 |
| --- | --- |
| `sub` | 用户 ID |
| `email` | 邮箱 |
| `role` | 角色 |
| `jti` | Token 唯一 ID |
| `tokenVersion` | Token 版本号 |
| `iat` | 签发时间 |
| `exp` | 过期时间 |

不要放入：

- 密码
- 真实姓名
- 手机号
- 报名信息
- 任何敏感业务字段

## 12.2 JwtTokenService 需要提供的方法

- `String generateToken(User user, boolean rememberMe)`
- `JwtClaims parse(String token)`
- `boolean isExpired(JwtClaims claims)`
- `boolean isBlacklisted(String jti)`
- `void blacklist(String jti, Duration ttl)`

## 12.3 过期策略

- 普通登录：2 小时
- 记住我：30 天
- 这些值放配置，不写死在代码里

## 13. Cookie 设计

Cookie 名建议：`lab_recruit_token`

属性要求：

- `HttpOnly=true`
- `Path=/`
- `SameSite=Lax`
- `Secure` 生产环境必须开启

实现要求：

- 登录成功时写入 Cookie
- 退出登录时覆盖空值并设置 `Max-Age=0`
- 修改密码和重置密码后也要主动清理 Cookie

建议单独封装：

- `AuthCookieService.writeLoginCookie(...)`
- `AuthCookieService.clearLoginCookie(...)`

不要在 Controller 里手动拼 Cookie 字符串。

## 14. JwtAuthenticationFilter 实现要求

### 14.1 过滤器职责

过滤器只做认证，不做业务授权。职责如下：

1. 从 Cookie 中读取 JWT
2. 若无 Token，直接放行
3. 若有 Token，解析并校验
4. 检查是否过期
5. 检查 `jti` 是否在 Redis 黑名单
6. 检查 `tokenVersion` 是否与数据库一致
7. 通过后构建 `Authentication`
8. 放入 `SecurityContext`

### 14.2 失败处理原则

- Token 缺失：不报错，继续后续链路
- Token 非法或过期：清空上下文，交给未登录处理器
- Token 对应用户不存在或被禁用：按未登录处理

### 14.3 不要在过滤器里做的事

- 不要在这里判断组归属
- 不要在这里判断报名期或选拔期
- 不要直接返回业务错误码以外的零散 JSON

## 17. Redis 设计

## 17.1 Key 规范

统一通过 `RedisKeyBuilder` 生成，禁止手写散落字符串。

推荐 Key：

```text
auth:email-code:{scene}:{email}
auth:email-send-cooldown:{scene}:{email}
auth:jwt:blacklist:{jti}
auth:login:fail:{email}
auth:login:lock:{email}
```

## 17.2 TTL 建议

| Key | TTL |
| --- | --- |
| 邮箱验证码 | 5 分钟 |
| 验证码发送冷却 | 60 秒 |
| 登录失败计数 | 15 分钟 |
| 登录锁定 | 15 分钟 |
| JWT 黑名单 | Token 剩余有效期 |

## 17.3 使用规则

- 验证码使用后立即删除
- 登出时将 `jti` 写入黑名单
- 修改密码或重置密码后，旧 Token 通过 `tokenVersion` 失效，不要求枚举所有 Token

## 18. DTO 与 VO 清单

认证模块建议至少实现以下 DTO：

- `SendEmailCodeRequest`
- `RegisterRequest`
- `LoginRequest`
- `ForgotPasswordRequest`
- `ResetPasswordRequest`
- `ChangePasswordRequest`

建议至少实现以下 VO：

- `CurrentUserVo`
- `LoginResultVo`
- `RegisterResultVo`

### 18.1 DTO 校验建议

`RegisterRequest`：

- `username`：`@NotBlank` + 长度限制 + 正则
- `email`：`@Email`
- `password`：`@NotBlank`
- `confirmPassword`：`@NotBlank`
- `code`：`@NotBlank`

额外逻辑校验：

- `password.equals(confirmPassword)`
- 密码必须同时包含字母和数字

报名与分组相关 DTO 还应额外校验：

- `grade` 必须落在 `GradeType` 枚举内
- `admissionYear` 必须是四位整数
- `admissionYear` 不得晚于当前年份
- `admissionYear` 不得早于合理下限，建议用 `当前年份 - 10`
- 当前招新默认只接受 `YEAR_1` 和 `YEAR_2` 报名时，应在 Service 层明确拒绝其他年级
- 同一用户新增申请时，应校验 `directionLevel2Id` 不重复
- 同一申请被分组后，不得再次进入其他分组

## 20. 注册实现步骤

### 20.1 `sendEmailCode`

流程：

1. 校验邮箱格式
2. 校验 `scene`
3. 检查发送冷却 Key
4. `REGISTER` 场景下要求邮箱未注册
5. `RESET_PASSWORD` 场景下要求邮箱已存在
6. 生成 6 位数字验证码
7. 写入 Redis，TTL 5 分钟
8. 写入发送冷却 Key，TTL 60 秒
9. 调用 `MailService`

### 20.2 `register`

流程：

1. `PeriodService.assertRegistrationOpenForRegister()`
2. 校验用户名格式
3. 校验邮箱未被占用
4. 校验用户名未被占用
5. 校验密码强度
6. 校验确认密码一致
7. 从 Redis 取验证码
8. 比对验证码
9. 生成 BCrypt 哈希
10. 保存 `User`
11. 默认：
    - `role=FRESHMAN`
    - `status=ACTIVE`
    - `emailVerified=true`
    - `tokenVersion=0`
12. 删除验证码缓存
13. 返回注册结果

### 20.3 伪代码

```java
public RegisterResultVo register(RegisterRequest request) {
    periodService.assertRegistrationOpenForRegister();
    validateRegisterRequest(request);
    ensureUsernameNotExists(request.username());
    ensureEmailNotExists(request.email());
    emailCodeService.verifyOrThrow(REGISTER, request.email(), request.code());

    User user = new User();
    user.setUsername(request.username());
    user.setEmail(request.email());
    user.setPasswordHash(passwordEncoder.encode(request.password()));
    user.setRole(UserRole.FRESHMAN);
    user.setStatus(UserStatus.ACTIVE);
    user.setEmailVerified(true);
    user.setTokenVersion(0L);
    userRepository.save(user);

    emailCodeService.delete(REGISTER, request.email());
    return RegisterResultVo.from(user);
}
```

## 21. 登录实现步骤

### 21.1 登录前检查

- 邮箱不能为空
- 密码不能为空
- 邮箱未被锁定

### 21.2 登录流程

1. 根据邮箱查用户
2. 用户不存在时累加失败次数
3. 用户被禁用时拒绝登录
4. 比较密码
5. 密码不正确时累加失败次数
6. 超过最大失败次数后写锁定 Key
7. 登录成功后：
   - 清理失败计数
   - 生成 JWT
   - 写入 Cookie
   - 更新 `lastLoginAt`
8. 返回用户信息

### 21.3 `rememberMe`

- `false`：普通过期时间
- `true`：使用更长 JWT 和 Cookie TTL

### 21.4 登录返回

返回：

- 用户 ID
- 用户名
- 邮箱
- 角色
- 当前组信息，可选

不要返回：

- `passwordHash`
- `token`

---

## 22. 退出登录实现步骤

### 22.1 流程

1. 从当前请求解析 Token
2. 若 Token 存在，取出 `jti`
3. 根据 Token 剩余有效期写入黑名单
4. 清空 Cookie
5. 返回成功

### 22.2 说明

- 仅清 Cookie 不够
- 必须配合黑名单，避免旧 Cookie 在某些场景下被重放

---

## 23. 找回密码与重置密码实现步骤

### 23.1 forgotPassword

建议直接复用 `sendEmailCode(scene=RESET_PASSWORD)` 逻辑。

### 23.2 resetPassword

流程：

1. 校验邮箱存在
2. 校验验证码正确
3. 校验新密码强度
4. 校验确认密码一致
5. 更新 `passwordHash`
6. `tokenVersion = tokenVersion + 1`
7. 删除验证码缓存
8. 清除登录 Cookie

### 23.3 为什么用 `tokenVersion`

用户可能在多个设备已登录。  
重置密码后，不需要遍历所有旧 Token，只需让数据库中 `tokenVersion` 增加。  
过滤器在校验 Token 时发现版本不一致，就会拒绝旧 Token。

---

## 24. 修改密码实现步骤

流程：

1. 当前用户必须已登录
2. 查当前用户
3. 校验旧密码正确
4. 校验新密码强度
5. 校验确认密码一致
6. 若新旧密码相同，可拒绝或允许，建议拒绝
7. 更新 `passwordHash`
8. `tokenVersion + 1`
9. 清空当前 Cookie
10. 返回成功，要求前端重新登录

## 25. PeriodService 设计

`PeriodService` 不应只返回当前时期，还要负责断言能力。

建议提供：

- `RecruitmentPeriodType getCurrentPeriod()`
- `boolean isRegistrationOpen()`
- `boolean isSelectionOpen()`
- `void assertRegistrationOpenForRegister()`
- `void assertRegistrationOpenForApplication()`
- `void assertSelectionOpenForTaskSubmit()`
- `void assertSelectionOpenForGrouping()`

### 25.1 当前时期推导逻辑

1. 读取启用中的时期配置
2. 若当前时间落在 `REGISTRATION` 区间，返回 `REGISTRATION`
3. 若落在 `SELECTION` 区间，返回 `SELECTION`
4. 若落在 `INTERVIEW` 区间，返回 `INTERVIEW`
5. 若晚于 `INTERVIEW.endTime`，返回 `FINISHED`
6. 其他情况视为“未开放”，可按项目需要返回 `FINISHED` 或单独异常；本项目建议返回 `FINISHED`

## 26. AuthzService 设计

`AuthzService` 负责资源归属判断，供 `@PreAuthorize` 调用。

建议提供的方法：

- `boolean isCurrentUser(Long userId)`
- `boolean canAccessApplication(Authentication authentication, Long targetUserId)`
- `boolean canViewGroup(Authentication authentication, Long groupId)`
- `boolean canManageGroup(Authentication authentication, Long groupId)`
- `boolean canPublishGroupAnnouncement(Authentication authentication, Long groupId)`
- `boolean canManageTask(Authentication authentication, Long taskId)`
- `boolean canReviewSubmission(Authentication authentication, Long submissionId)`

### 26.1 实现原则

- `ADMIN` 直接通过
- `LEADER` 需要校验自己是否是该组负责人
- `FRESHMAN` 只允许访问自己的资源

### 26.2 不要这样做

不要在每个 Controller 方法里写：

```java
if (!group.getLeaderId().equals(currentUserId)) {
    throw new ForbiddenException();
}
```

正确做法是：

```java
@PreAuthorize("@authzService.canManageGroup(authentication, #groupId)")
```

---

## 27. 注解使用规范

### 27.1 基础角色校验

```java
@PreAuthorize("hasRole('ADMIN')")
```

```java
@PreAuthorize("hasAnyRole('LEADER', 'ADMIN')")
```

### 27.2 资源归属校验

```java
@PreAuthorize("@authzService.isCurrentUser(#userId)")
```

```java
@PreAuthorize("@authzService.canViewGroup(authentication, #groupId)")
```

### 27.3 时期校验

时期校验不要全塞进注解表达式里。  
推荐方式：

- 基础角色和资源归属：注解
- 业务时期：Service 方法内部 `assert`

原因：

- 时期错误需要清晰业务消息
- Service 内部更容易复用和调试

例如提交任务：

```java
@PreAuthorize("@authzService.isCurrentUser(#currentUserId)")
public void submitTask(Long currentUserId, Long taskId, SubmitTaskRequest request) {
    periodService.assertSelectionOpenForTaskSubmit();
    ...
}
```

## 31. 测试清单

认证模块如果没有测试，后续权限问题会非常难排查。  
至少补以下测试：

### 31.1 注册测试

- 正常注册成功
- 邮箱重复注册失败
- 用户名重复注册失败
- 验证码错误失败
- 非报名期注册失败
- 密码不符合规则失败

### 31.2 登录测试

- 正常登录成功
- 密码错误失败
- 用户不存在失败
- 账号禁用失败
- 失败次数超过限制后锁定
- `rememberMe` 写入长效 Cookie

### 31.3 Token 测试

- 正常 Token 可通过过滤器
- 过期 Token 被拒绝
- 黑名单 Token 被拒绝
- `tokenVersion` 不匹配被拒绝

### 31.4 密码测试

- 找回密码成功
- 修改密码成功
- 修改密码后旧 Token 失效
- 重置密码后旧 Token 失效

### 31.5 权限测试

- 匿名访问受保护接口返回 401
- 新生访问 `/api/v1/admin/**` 返回 403
- 负责人访问非自己组资源返回 403
- 管理员访问任意受保护资源成功

## 32. 常见错误实现，必须避免

### 32.1 错误一：把 Token 放 localStorage

原因：

- 容易被 XSS 读取
- 与当前方案不一致

### 32.2 错误二：负责人权限只校验 `ROLE_LEADER`

原因：

- 会导致负责人能操作其他组资源

### 32.3 错误三：登出时只删 Cookie 不进黑名单

原因：

- 旧 Token 可能在其他客户端继续可用

### 32.4 错误四：修改密码不更新 `tokenVersion`

原因：

- 无法使旧 Token 失效

### 32.5 错误五：时期判断散落在 Controller

原因：

- 不可复用
- 不易测试
- 容易遗漏

## 34. 结论

按本文档实现时，要始终保持下面的职责边界：

1. `SecurityConfig + JwtAuthenticationFilter` 负责“识别当前用户”
2. `@PreAuthorize + AuthzService` 负责“是否有权访问该资源”
3. `PeriodService` 负责“当前时期是否允许该动作”
4. `AuthService` 负责“认证业务流程”
5. `Redis` 负责“验证码、黑名单、限流等临时状态”

只要严格按这套边界实现，开发者就可以直接在此基础上扩展报名、分组、公告、资料和任务模块，而不需要重构认证和权限体系。
