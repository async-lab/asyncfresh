本文档基于当前 `backend` 仓库的实际实现整理，不是需求草案。

当前已经实现的后端模块有：

- 认证与会话模块
- 当前时期与方向公共查询模块
- 报名模块
- 报名审核流转模块
- 分组查询与分组管理模块
- 分组基础设施管理模块
- 任务模块
- 公告模块
- 组内学习资料模块

## 2. 启动与基础设施约束

### 2.1 基础依赖

系统启动依赖以下基础设施：

- MySQL
- Redis
- SMTP 邮件服务
- 本地文件存储目录

其中：

- Redis 是硬依赖。启动阶段会执行 `PING` 检查，Redis 不可用时应用直接拒绝启动。
- SMTP 是启动期硬校验依赖。若 `MAIL_SMTP_HOST`、`MAIL_ACCOUNT`、`MAIL_AUTH_CODE` 任一缺失，应用会在启动阶段直接失败。
- 本地文件存储目录会在首次使用时自动创建父目录。

### 2.3 默认管理员初始化

系统启动后会执行默认管理员初始化逻辑：

- 若 `app.bootstrap.default-admin.enabled=false`，直接跳过。
- 若库中已存在任意 `ADMIN` 用户，直接跳过。
- 若开启初始化但未配置 `DEFAULT_ADMIN_USERNAME` / `DEFAULT_ADMIN_PASSWORD` / `DEFAULT_ADMIN_EMAIL`，启动失败。
- 初始化时使用 MySQL `GET_LOCK` 做互斥，避免多实例重复创建。

默认管理员特点：

- `role=ADMIN`
- `status=ACTIVE`
- `emailVerified=true`
- 不走邮箱验证码流程

## 3. 当前系统核心流程

## 3.1 认证与会话流程

### 3.1.1 注册流程

1. 前端调用 `POST /api/v1/auth/send-email-code`，场景为 `REGISTER`。
2. 后端要求当前必须处于报名期。
3. 若邮箱已注册，直接返回冲突。
4. 若未触发发送冷却，则生成 6 位数字验证码，写入 Redis，并发送邮件。
5. 前端带验证码调用 `POST /api/v1/auth/register`。
6. 后端校验：
   - 当前必须处于报名期
   - 两次密码一致
   - 密码至少 8 位且必须同时包含字母和数字
   - 用户名未占用
   - 邮箱未占用
   - 验证码正确且未锁定
7. 注册成功后创建用户，默认：
   - `role=FRESHMAN`
   - `status=ACTIVE`
   - `emailVerified=true`
   - `tokenVersion=0`
8. 注册成功后删除 Redis 中对应验证码。

### 3.1.2 登录流程

1. 前端调用 `POST /api/v1/auth/login`。
2. 后端根据 `email + clientIp` 构造登录限流键。
3. 若该键已被锁定，返回 429。
4. 校验邮箱是否存在、密码是否正确、用户状态是否为 `ACTIVE`。
5. 任一校验失败时，累计失败次数；达到上限后锁定该键。
6. 登录成功后：
   - 清空失败计数
   - 更新 `lastLoginAt`
   - 签发 JWT
   - 写入 HttpOnly 登录 Cookie
   - 写入非 HttpOnly 的 CSRF Cookie
7. 返回登录成功结果，不直接返回 JWT。

### 3.1.3 登录限流 IP 解析规则

当前实现已经修复伪造代理头问题：

- 默认仅信任 `request.getRemoteAddr()`
- 只有 `app.auth.login.trust-forward-headers=true` 且 `remoteAddr` 命中可信代理名单时，才解析 `X-Forwarded-For` / `X-Real-IP`
- `X-Forwarded-For` 采用从右向左剥离可信代理的方式识别真实客户端 IP
- 非法 IP、空值、异常链条统一回退到 `remoteAddr`

### 3.1.4 当前用户读取流程

`GET /api/v1/auth/me` 返回：

- 基础用户信息
- 是否已验证邮箱
- 若当前用户是负责人，则返回其负责分组列表 `leaderGroups`
- 当前用户所在的所有分组简表

### 3.1.5 登出与密码变更流程

登出流程：

- `POST /api/v1/auth/logout`
- 若当前请求携带有效 JWT，则将其加入 Redis 黑名单直到自然过期
- 清空登录 Cookie 与 CSRF Cookie

忘记密码流程：

1. `POST /api/v1/auth/forgot-password`
2. 实际内部复用验证码发送逻辑，场景为 `RESET_PASSWORD`
3. 若邮箱不存在，不暴露该事实，仍返回统一成功消息
4. `POST /api/v1/auth/reset-password`
5. 校验重置验证码与新密码
6. 修改密码并 `tokenVersion + 1`，强制所有旧登录态失效

修改密码流程：

1. `POST /api/v1/auth/change-password`
2. 需要先登录
3. 校验旧密码
4. 校验新密码规则
5. 修改密码并 `tokenVersion + 1`
6. 当前请求中的旧 Token 会被加入黑名单
7. 清空登录 Cookie，要求重新登录

## 3.2 时期控制流程

系统维护三类可配置时期：

- `REGISTRATION`
- `SELECTION`
- `INTERVIEW`

系统额外会推导两个只读状态：

- `NOT_OPEN`
- `FINISHED`

当前时期判定顺序：

1. 若报名期当前开启，返回 `REGISTRATION`
2. 否则若选拔期开启，返回 `SELECTION`
3. 否则若面试期开启，返回 `INTERVIEW`
4. 若没有任何启用时期，返回 `NOT_OPEN`
5. 若当前时间晚于所有启用时期的最晚结束时间，返回 `FINISHED`
6. 其余情况返回 `NOT_OPEN`

当前代码对业务的时期限制如下：

- 注册：仅报名期
- 发送注册验证码：仅报名期
- 报名创建 / 修改 / 撤回：仅报名期
- 分组管理：仅选拔期
- 任务发布 / 修改 / 删除 / 打回 / 评测：仅选拔期
- 任务提交：仅选拔期

## 3.3 方向管理流程

方向当前是二层结构：

- 一级方向：`level=1`，`parentId=null`
- 二级方向：`level=2`，必须挂在一级方向下

公共查询只返回“已启用方向”的树状结构，不再对匿名用户暴露禁用方向。

管理员可新增、修改、删除方向。当前约束：

- 同级方向名不能重复
- 二级方向只能挂在一级方向下
- 方向不能把自己设为父级
- 一级方向若存在下级方向，不能直接改成二级方向
- 已被报名或分组引用的方向，不能修改层级归属
- 已被报名或分组引用的方向，不能删除

## 3.4 报名流程

当前报名对象是“用户先按方向提交报名申请”，后续再由管理员或负责人按组进行分配。数据模型上，申请本身只保存方向与个人信息，不直接绑定组。

### 3.4.1 报名创建

1. 当前用户必须已登录且角色为 `FRESHMAN`
2. 当前必须处于报名期
3. `grade` 必须在配置 `app.recruitment.application.allowed-grades` 中
4. `admissionYear` 必须在 `[当前年 - 6, 当前年 + 1]`
5. 一级方向必须存在、启用且 `level=1`
6. 二级方向必须存在、启用且 `level=2`
7. 二级方向必须隶属于所选一级方向
8. 同一用户在同一个二级方向下最多只能提交一份申请
9. 保存成功后状态默认为 `SUBMITTED`

### 3.4.2 报名修改

修改流程和创建流程基本一致，但额外要求：

- 只能修改自己的申请
- 当前必须是 `SUBMITTED` 状态
- 若已经进入 `group_member`，即使状态仍是 `SUBMITTED` 也不允许修改
- 修改走申请行锁，防止与分组并发冲突

### 3.4.3 报名撤回

撤回约束：

- 只能撤回自己的申请
- 当前必须处于报名期
- 当前必须是 `SUBMITTED` 状态
- 若已经分组，不允许撤回
- 撤回后状态变为 `WITHDRAWN`

### 3.4.4 报名汇总

报名汇总返回：

- `applicationCount`：申请总数
- `submittedCount`：仍待处理、且未进入组的申请数量
- `groupedCount`：已分组申请数量
- `groupIds`：当前用户已进入的分组 ID 列表

## 3.5 分组流程

当前分组是“将某份未分组申请放入某个分组”，分组关系实际由 `group_member` 表承载。

### 3.5.1 可见范围

管理员：

- 可查看全部分组
- 可查看全部未分组申请
- 可将任意未分组申请分配到任意分组

负责人：

- 可查看自己负责的分组列表
- 可查看全部未分组申请
- 只能将申请分配到自己负责的组

普通新生：

- 可查看自己所在分组详情
- 不可查看组员列表
- 不可进行分组管理

额外能力：

- 管理员可创建 / 修改 / 删除分组
- 管理员可任命 / 撤销分组负责人
- 管理员可拒绝未分组申请
- 负责人可拒绝“与自己负责分组条件匹配”的未分组申请
- 管理员和负责人都可将已分组申请从组内移出，但负责人仅能操作自己负责的组

### 3.5.2 分组条件

申请能被放入某个组时，必须同时满足：

- 当前处于选拔期
- 申请状态为 `SUBMITTED`
- 申请尚未有 `group_member` 记录
- 申请的一级方向、二级方向、年级、入学年份，与目标组完全一致
- 目标组当前人数小于 `maxSize`

### 3.5.3 并发控制

当前代码已经实现并发分组保护：

- 固定加锁顺序：先锁分组，再锁申请
- 分组人数检查使用锁定读
- `group_member.application_id` 有唯一约束兜底

这意味着：

- 同一申请不会被同时分到两个组
- 同一个组不会在并发下超出 `maxSize`
- 报名修改 / 撤回与分组也不会互相覆盖状态

### 3.5.4 审核流转

当前系统已实现两类审核流转：

- 拒绝申请：`SUBMITTED -> REJECTED`
- 取消分组：`GROUPED -> SUBMITTED`

拒绝申请约束：

- 当前必须处于选拔期
- 申请必须是未分组的 `SUBMITTED`
- 拒绝时必须填写备注，写入 `statusRemark`
- 管理员可拒绝任意未分组申请
- 负责人仅可拒绝与自己负责分组条件匹配的申请

取消分组约束：

- 当前必须处于选拔期
- 申请当前必须已在目标组内，且状态为 `GROUPED`
- 管理员可从任意组取消分组
- 负责人仅可从自己负责的组取消分组
- 取消分组后状态回到 `SUBMITTED`
- 可选备注会写入 `statusRemark`

### 3.5.5 分组基础设施管理

当前系统已支持管理员维护分组本身：

- 创建分组
- 修改分组
- 删除空分组
- 指派负责人
- 撤销负责人

当前约束：

- 分组名称全局唯一
- 一级 / 二级方向必须存在且层级关系合法
- `maxSize` 必须大于 0
- 若分组内已有成员，不允许修改方向、年级、入学年份
- 若分组内已有成员，不允许把 `maxSize` 改小到当前人数以下
- 分组内仍有成员时不允许删除
- 只能把角色为 `LEADER` 且状态为 `ACTIVE` 的用户设为负责人

## 3.6 任务流程

当前任务是严格的“组内任务”模型，不支持全局任务。

### 3.6.1 发布与维护

管理员和负责人都可以在自己可管理的组内发布任务。

发布和修改任务时要求：

- 当前必须处于选拔期
- 只能操作自己可管理的组
- `title` 必填，最长 100
- `contentMarkdown` 最长 20000
- `attachmentFileId` 可空
- `contentMarkdown` 与任务附件不能同时为空
- `maxScore` 范围为 `1..100`
- `deadlineAt` 必须晚于当前时间

更新任务时支持三种附件行为：

- 保留原附件
- 替换为新附件
- 显式移除原附件

删除任务时：

- 会删除任务本身
- 会删除该任务下所有成员提交记录
- 会删除关联的任务附件与提交附件

### 3.6.2 成员查看与提交

新生只能查看自己所在组的任务。

提交规则：

- 当前必须处于选拔期
- 当前用户必须属于该任务所在组
- 当前时间不能晚于任务截止时间
- 提交内容和提交附件不能同时为空
- 每个用户对每个任务默认只允许提交一次
- 若需要再次提交，必须由负责人或管理员执行“打回”

### 3.6.3 打回与重新提交

当前实现的打回语义是“回滚到待提交”，不是保留历史版本。

打回时会执行：

- `status -> PENDING`
- 删除当前提交的正文内容
- 删除当前提交附件引用
- 清空提交时间、评测人、分数、评语、评测时间
- 若原提交带附件，则同时删除对应本地文件

打回后，成员仍然只能在原任务截止时间前重新提交。

### 3.6.4 评测流转

任务提交状态使用：

- `PENDING`：待提交
- `SUBMITTED`：已提交待评测
- `REVIEWED`：已评测

评测规则：

- 当前必须处于选拔期
- 管理员可评测任意组任务
- 负责人只能评测自己负责组的任务
- 只能评测本组成员的提交
- 评分范围为 `0..maxScore`
- 评语可空
- 已评测提交允许再次评测，后一次覆盖前一次结果
- 已评测提交也允许被打回，再次回到 `PENDING`

## 3.7 公告流程

公告分为两类：

- 全局公告 `GLOBAL`
- 组内公告 `GROUP`

### 3.7.1 发布与修改

管理员：

- 可发布全局公告
- 可发布任意组内公告
- 可修改和删除全部公告

负责人：

- 只能发布自己负责分组的组内公告
- 不能发布全局公告
- 只能修改和删除自己负责组的组内公告

当前约束：

- `title` 必填，最长 100
- `contentMarkdown` 必填，最长 20000
- `scope=GROUP` 时必须带 `groupId`
- `scope=GLOBAL` 时 `groupId` 会被忽略并持久化为 `null`

### 3.7.2 可见范围

管理员可查看全部公告。

其他登录用户：

- 可查看全部全局公告
- 可查看自己所在组的组内公告
- 若自己是某组负责人，也可查看自己负责组的组内公告

## 3.8 组内学习资料流程

当前学习资料是“组内资料”模型，不支持全局资料。

### 3.8.1 发布与修改

管理员和负责人都可以在自己可管理的组内维护资料。

当前约束：

- `title` 必填，最长 100
- `contentMarkdown` 最长 20000
- `attachmentFileId` 可空
- 资料正文和资料附件不能同时为空
- 修改时支持保留、替换、删除附件
- 删除资料时若存在附件，会同时删除本地文件

### 3.8.2 可见范围

管理员可查看全部资料。

其他登录用户：

- 只能查看自己所在组的资料
- 若自己是某组负责人，也可查看自己负责组的资料

## 3.9 文件上传与本地附件流程

### 3.9.1 用途枚举

当前附件用途包括：

- `TASK_ATTACHMENT`
- `TASK_SUBMISSION_ATTACHMENT`
- `MATERIAL_ATTACHMENT`

### 3.9.2 直传与分片策略

系统支持两种上传模式：

- 直传
- 分片上传

行为由 `app.storage.chunk-size` 控制：

- `0B`：不启用分片上传，只允许直传
- `>0`：启用分片上传，直传接口会拒绝，要求走上传会话

### 3.9.3 文件约束

公共约束：

- 文件名不能为空
- 文件大小必须大于 0
- 附件保存到 `app.storage.root-path` 下的本地目录
- 数据库只保存相对路径和文件元信息
- 文件下载必须经过受权限控制的后端接口

任务相关额外约束：

- `TASK_ATTACHMENT` 与 `TASK_SUBMISSION_ATTACHMENT` 会校验 `app.task.attachment-max-size`
- `MATERIAL_ATTACHMENT` 不额外校验该配置，只受 Spring multipart 总体大小限制

### 3.9.4 附件绑定规则

上传完成后的附件默认处于“未绑定”状态。

只有上传者本人可以：

- 在后续创建任务、提交任务、创建资料时引用该附件
- 将未绑定附件绑定到业务对象

一旦已绑定：

- 同一附件不能再被其他业务对象重复使用

## 4.4 认证与 CSRF 约定

### 登录态

系统不使用 `Authorization` Header，而是使用 Cookie：

- 登录 Cookie：`lab_recruit_token`
- CSRF Cookie：`XSRF-TOKEN`

### 需要 CSRF 的请求

除以下公开写接口外，所有会修改状态的 `/api/**` 请求都需要：

- 请求头带 `X-CSRF-TOKEN`
- Cookie 中同时带 `XSRF-TOKEN`
- 两者都必须与当前登录态绑定的预期值一致

公开写接口不强制 CSRF：

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/register`
- `POST /api/v1/auth/send-email-code`
- `POST /api/v1/auth/forgot-password`
- `POST /api/v1/auth/reset-password`

### 文件下载接口

文件下载接口不走 `ApiResponse<T>`，直接返回二进制流：

- `Content-Type` 为文件类型或 `application/octet-stream`
- `Content-Disposition` 为附件下载

## 6.11 文件上传模块

### POST `/api/v1/uploads`

权限：

- 已登录

请求方式：

- `multipart/form-data`

请求参数：

- `purpose`：附件用途，放在查询参数
- `file`：二进制文件，放在表单字段

示例：

```text
POST /api/v1/uploads?purpose=TASK_ATTACHMENT
Content-Type: multipart/form-data
```

行为：

- 仅在 `app.storage.chunk-size=0` 时可用
- 若已启用分片上传，该接口返回冲突

返回 `StoredFileVo`：

```json
{
  "fileId": 1001,
  "purpose": "TASK_ATTACHMENT",
  "originalFileName": "task.pdf",
  "contentType": "application/pdf",
  "sizeBytes": 12345
}
```

### POST `/api/v1/uploads/sessions`

权限：

- 已登录

请求体：

```json
{
  "purpose": "TASK_SUBMISSION_ATTACHMENT",
  "fileName": "solution.zip",
  "contentType": "application/zip",
  "totalSize": 1048576
}
```

行为：

- 仅在 `app.storage.chunk-size>0` 时可用
- 创建上传会话

返回 `UploadSessionVo`：

```json
{
  "sessionId": 1,
  "chunkSizeBytes": 524288,
  "totalSize": 1048576,
  "nextChunkIndex": 0
}
```

### POST `/api/v1/uploads/sessions/{sessionId}/chunks/{chunkIndex}`

权限：

- 已登录
- 必须是会话创建者

请求方式：

- `multipart/form-data`

规则：

- 分片必须按顺序上传
- 每片大小不能超过配置片大小或剩余大小

返回：

- 更新后的 `UploadSessionVo`

### POST `/api/v1/uploads/sessions/{sessionId}/complete`

权限：

- 已登录
- 必须是会话创建者

规则：

- 只有全部分片上传完成后才能结束会话
- 结束后会生成正式附件记录 `StoredFileVo`

## 7. 当前接口与流程的已知实现边界

1. 当前负责人可以查看所有未分组申请，而不是仅查看与自己分组条件相关的申请。
2. 当前方向树只实现两层结构。
3. 当前系统认证缓存仅支持 Redis，不能切换为内存实现。
4. 当前任务只支持组内任务，不支持全局任务。
5. 当前学习资料只支持组内资料，不支持全局资料或方向级资料。
6. 当前文件上传只支持“整文件直传”或“严格顺序分片上传”，不支持乱序分片、秒传、断点恢复。
7. 当前任务打回会直接清空原提交内容和原提交附件，不保留历史版本链。
8. 当前导出统一为 `xlsx`，未提供 CSV、PDF 或异步导出任务。
9. 当前公告与资料列表未做分页。

## 8. 建议的前后端联调顺序

1. 配置好 MySQL、Redis、JWT 密钥、邮件服务、本地存储目录。
2. 确认默认管理员是否需要自动初始化。
3. 先调用：
   - `GET /api/v1/meta/current-period`
   - `GET /api/v1/directions`
4. 报名期内完成：
   - 注册验证码发送
   - 注册
   - 登录
   - `GET /api/v1/auth/me`
5. 使用新生账号联调报名：
   - 创建报名
   - 查看报名列表
   - 查看报名汇总
   - 修改报名
   - 撤回报名
6. 使用管理员或负责人账号联调分组：
   - 管理员创建分组
   - 管理员指派负责人
   - 查看可管理分组
   - 查看未分组申请
   - 将申请分配到组
   - 拒绝申请
   - 取消分组
   - 查看组详情与组员
7. 联调附件：
   - 根据 `app.storage.chunk-size` 决定走直传还是分片上传
   - 上传任务附件 / 提交附件 / 资料附件
8. 联调任务：
   - 管理员或负责人创建任务
   - 新生查看任务列表与详情
   - 新生提交任务
   - 管理员或负责人查看全组提交状态
   - 管理员或负责人评测任务
   - 管理员或负责人打回后重新提交
9. 联调公告与资料：
   - 管理员发布全局公告
   - 负责人发布组内公告
   - 管理员或负责人上传组内资料
   - 新生查看自己可见公告与资料
10. 联调看板与导出：
   - 管理员查看全局总览和组面板
   - 负责人查看自己组面板
   - 导出报名信息、组成员、任务结果
