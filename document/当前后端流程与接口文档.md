本文档基于当前 `backend` 项目的实际代码实现整理，不是需求草案。

当前已经实现的后端模块有：

- 认证与会话模块
- 当前时期与方向公共查询模块
- 报名模块
- 报名审核流转模块
- 分组查询与分组管理模块
- 分组基础设施管理模块
- 管理员用户管理模块
- 管理员时期配置模块

- 自动分组

## 2. 启动与基础设施约束

### 2.1 基础依赖

系统启动依赖以下基础设施：

- MySQL
- Redis
- SMTP 邮件服务

其中 Redis 当前是硬依赖。启动阶段会执行 `PING` 检查，Redis 不可用时应用直接拒绝启动。

SMTP 也是启动期硬校验依赖。若 `MAIL_SMTP_HOST`、`MAIL_ACCOUNT`、`MAIL_AUTH_CODE` 任一缺失，应用会在启动阶段直接失败，而不是等到发送验证码时再报错。

### 2.3 默认管理员初始化

系统启动后会执行默认管理员初始化逻辑：

- 若 `app.bootstrap.default-admin.enabled=false`，直接跳过。
- 若库中已存在任意 `ADMIN` 用户，直接跳过。
- 若开启初始化但未配置 `DEFAULT_ADMIN_USERNAME` / `DEFAULT_ADMIN_PASSWORD` / `DEFAULT_ADMIN_EMAIL`，启动失败。
- 初始化时使用 MySQL `GET_LOCK` 做互斥，避免多实例重复创建。

默认管理员特点：

- `role=ADMIN`
- `status=ACTIVE`
- `emailVerified=true`
- 不走邮箱验证码流程

## 3. 当前系统核心流程

## 3.1 认证与会话流程

### 3.1.1 注册流程

1. 前端调用 `POST /api/v1/auth/send-email-code`，场景为 `REGISTER`。
2. 后端要求当前必须处于报名期。
3. 若邮箱已注册，直接返回冲突。
4. 若未触发发送冷却，则生成 6 位数字验证码，写入 Redis，并发送邮件。
5. 前端带验证码调用 `POST /api/v1/auth/register`。
6. 后端校验：
   - 当前必须处于报名期
   - 两次密码一致
   - 密码至少 8 位且必须同时包含字母和数字
   - 用户名未占用
   - 邮箱未占用
   - 验证码正确且未锁定
7. 注册成功后创建用户，默认：
   - `role=FRESHMAN`
   - `status=ACTIVE`
   - `emailVerified=true`
   - `tokenVersion=0`
8. 注册成功后删除 Redis 中对应验证码。

### 3.1.2 登录流程

1. 前端调用 `POST /api/v1/auth/login`。
2. 后端根据 `email + clientIp` 构造登录限流键。
3. 若该键已被锁定，返回 429。
4. 校验邮箱是否存在、密码是否正确、用户状态是否为 `ACTIVE`。
5. 任一校验失败时，累计失败次数；达到上限后锁定该键。
6. 登录成功后：
   - 清空失败计数
   - 更新 `lastLoginAt`
   - 签发 JWT
   - 写入 HttpOnly 登录 Cookie
   - 写入非 HttpOnly 的 CSRF Cookie
7. 返回登录成功结果，不直接返回 JWT。

### 3.1.3 登录限流 IP 解析规则

当前实现已经修复伪造代理头问题：

- 默认仅信任 `request.getRemoteAddr()`
- 只有 `app.auth.login.trust-forward-headers=true` 且 `remoteAddr` 命中可信代理名单时，才解析 `X-Forwarded-For` / `X-Real-IP`
- `X-Forwarded-For` 采用从右向左剥离可信代理的方式识别真实客户端 IP
- 非法 IP、空值、异常链条统一回退到 `remoteAddr`

### 3.1.4 当前用户读取流程

`GET /api/v1/auth/me` 返回：

- 基础用户信息
- 是否已验证邮箱
- 若当前用户是负责人，则返回其最小的负责分组 ID 作为 `leaderGroupId`
- 当前用户所在的所有分组简表

### 3.1.5 登出与密码变更流程

登出流程：

- `POST /api/v1/auth/logout`
- 若当前请求携带有效 JWT，则将其加入 Redis 黑名单直到自然过期
- 清空登录 Cookie 与 CSRF Cookie

忘记密码流程：

1. `POST /api/v1/auth/forgot-password`
2. 实际内部复用验证码发送逻辑，场景为 `RESET_PASSWORD`
3. 若邮箱不存在，不暴露该事实，仍返回统一成功消息
4. `POST /api/v1/auth/reset-password`
5. 校验重置验证码与新密码
6. 修改密码并 `tokenVersion + 1`，强制所有旧登录态失效

修改密码流程：

1. `POST /api/v1/auth/change-password`
2. 需要先登录
3. 校验旧密码
4. 校验新密码规则
5. 修改密码并 `tokenVersion + 1`
6. 当前请求中的旧 Token 会被加入黑名单
7. 清空登录 Cookie，要求重新登录

## 3.2 时期控制流程

系统维护三类可配置时期：

- `REGISTRATION`
- `SELECTION`
- `INTERVIEW`

系统额外会推导两个只读状态：

- `NOT_OPEN`
- `FINISHED`

当前时期判定顺序：

1. 若报名期当前开启，返回 `REGISTRATION`
2. 否则若选拔期开启，返回 `SELECTION`
3. 否则若面试期开启，返回 `INTERVIEW`
4. 若没有任何启用时期，返回 `NOT_OPEN`
5. 若当前时间晚于所有启用时期的最晚结束时间，返回 `FINISHED`
6. 其余情况返回 `NOT_OPEN`

当前代码对业务的时期限制如下：

- 注册：仅报名期
- 发送注册验证码：仅报名期
- 报名创建 / 修改 / 撤回：仅报名期
- 分组管理：仅选拔期

## 3.3 方向管理流程

方向当前是二层结构：

- 一级方向：`level=1`，`parentId=null`
- 二级方向：`level=2`，必须挂在一级方向下

公共查询只返回“已启用方向”的树状结构，不再对匿名用户暴露禁用方向。

管理员可新增、修改、删除方向。当前约束：

- 同级方向名不能重复
- 二级方向只能挂在一级方向下
- 方向不能把自己设为父级
- 一级方向若存在下级方向，不能直接改成二级方向
- 已被报名或分组引用的方向，不能修改层级归属
- 已被报名或分组引用的方向，不能删除

## 3.4 报名流程

当前报名对象是“用户先按方向提交报名申请”，后续再由管理员或负责人按组进行分配。数据模型上，申请本身只保存方向与个人信息，不直接绑定组。

### 3.4.1 报名创建

1. 当前用户必须已登录且角色为 `FRESHMAN`
2. 当前必须处于报名期
3. `grade` 必须在配置 `app.recruitment.application.allowed-grades` 中
4. `admissionYear` 必须在 `[当前年 - 6, 当前年 + 1]`
5. 一级方向必须存在、启用且 `level=1`
6. 二级方向必须存在、启用且 `level=2`
7. 二级方向必须隶属于所选一级方向
8. 同一用户在同一个二级方向下最多只能提交一份申请
9. 保存成功后状态默认为 `SUBMITTED`

### 3.4.2 报名修改

修改流程和创建流程基本一致，但额外要求：

- 只能修改自己的申请
- 当前必须是 `SUBMITTED` 状态
- 若已经进入 `group_member`，即使状态仍是 `SUBMITTED` 也不允许修改
- 修改走申请行锁，防止与分组并发冲突

### 3.4.3 报名撤回

撤回约束：

- 只能撤回自己的申请
- 当前必须处于报名期
- 当前必须是 `SUBMITTED` 状态
- 若已经分组，不允许撤回
- 撤回后状态变为 `WITHDRAWN`

### 3.4.4 报名汇总

报名汇总返回：

- `applicationCount`：申请总数
- `submittedCount`：仍待处理、且未进入组的申请数量
- `groupedCount`：已分组申请数量
- `groupIds`：当前用户已进入的分组 ID 列表

## 3.5 分组流程

当前分组是“将某份未分组申请放入某个分组”，分组关系实际由 `group_member` 表承载。

### 3.5.1 可见范围

管理员：

- 可查看全部分组
- 可查看全部未分组申请
- 可将任意未分组申请分配到任意分组

负责人：

- 可查看自己负责的分组列表
- 可查看全部未分组申请
- 只能将申请分配到自己负责的组

普通新生：

- 可查看自己所在分组详情
- 不可查看组员列表
- 不可进行分组管理

额外能力：

- 管理员可创建 / 修改 / 删除分组
- 管理员可任命 / 撤销分组负责人
- 管理员可拒绝未分组申请
- 负责人可拒绝“与自己负责分组条件匹配”的未分组申请
- 管理员和负责人都可将已分组申请从组内移出，但负责人仅能操作自己负责的组

### 3.5.2 分组条件

申请能被放入某个组时，必须同时满足：

- 当前处于选拔期
- 申请状态为 `SUBMITTED`
- 申请尚未有 `group_member` 记录
- 申请的一级方向、二级方向、年级、入学年份，与目标组完全一致
- 目标组当前人数小于 `maxSize`

### 3.5.3 并发控制

当前代码已经实现并发分组保护：

- 固定加锁顺序：先锁分组，再锁申请
- 分组人数检查使用锁定读
- `group_member.application_id` 有唯一约束兜底

这意味着：

- 同一申请不会被同时分到两个组
- 同一个组不会在并发下超出 `maxSize`
- 报名修改 / 撤回与分组也不会互相覆盖状态

### 3.5.4 审核流转

当前系统已实现两类审核流转：

- 拒绝申请：`SUBMITTED -> REJECTED`
- 取消分组：`GROUPED -> SUBMITTED`

拒绝申请约束：

- 当前必须处于选拔期
- 申请必须是未分组的 `SUBMITTED`
- 拒绝时必须填写备注，写入 `statusRemark`
- 管理员可拒绝任意未分组申请
- 负责人仅可拒绝与自己负责分组条件匹配的申请

取消分组约束：

- 当前必须处于选拔期
- 申请当前必须已在目标组内，且状态为 `GROUPED`
- 管理员可从任意组取消分组
- 负责人仅可从自己负责的组中取消分组
- 取消分组后状态回到 `SUBMITTED`
- 可选备注会写入 `statusRemark`

### 3.5.5 分组基础设施管理

当前系统已支持管理员维护分组本身：

- 创建分组
- 修改分组
- 删除空分组
- 指派负责人
- 撤销负责人

当前约束：

- 分组名称全局唯一
- 一级 / 二级方向必须存在且层级关系合法
- `maxSize` 必须大于 0
- 若分组内已有成员，不允许修改方向、年级、入学年份
- 若分组内已有成员，不允许把 `maxSize` 改小到当前人数以下
- 分组内仍有成员时不允许删除
- 只能把角色为 `LEADER` 且状态为 `ACTIVE` 的用户设为负责人

## 3.6 管理员用户管理流程

管理员用户管理支持：

- 分页查询用户列表
- 按角色、状态、关键字过滤
- 查询用户详情
- 修改用户状态

当前约束：

- 只有 `ADMIN` 可以调用
- 管理员不能修改自己的状态

## 4. 通用接口约定

## 4.1 响应包裹格式

所有接口统一返回 `ApiResponse<T>`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "timestamp": 1710000000000,
  "requestId": "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `code` | 业务码，成功固定为 `0` |
| `message` | 业务消息 |
| `data` | 返回数据 |
| `timestamp` | 服务端时间戳，毫秒 |
| `requestId` | 请求唯一标识，同时也会出现在响应头 `X-Request-Id` |

## 4.2 分页结构

分页接口 `data` 使用 `PageResult<T>`：

```json
{
  "list": [],
  "page": 1,
  "size": 10,
  "total": 0,
  "totalPages": 0
}
```

## 4.3 常见错误码

| HTTP 状态 | 业务码 | 含义 |
| --- | --- | --- |
| `400` | `40000` | 参数错误 |
| `401` | `40100` | 未登录或登录已过期 |
| `403` | `40300` | 无权限访问 |
| `403` | `40310` | 当前时期不允许操作 |
| `404` | `40400` | 资源不存在 |
| `409` | `40900` | 数据冲突 |
| `409` | `40910` | 业务状态冲突 |

字段校验失败时，`data` 结构为：

```json

    {
      "field": "email",

    }
  ]

```

## 4.4 认证与 CSRF 约定

### 登录态

系统不使用 `Authorization` Header，而是使用 Cookie：

- 登录 Cookie：`lab_recruit_token`
- CSRF Cookie：`XSRF-TOKEN`

### 需要 CSRF 的请求

除以下公开写接口外，所有会修改状态的 `/api/**` 请求都需要：

- 请求头带 `X-CSRF-TOKEN`
- Cookie 中同时带 `XSRF-TOKEN`
- 两者都必须与当前登录态绑定的预期值一致

公开写接口不强制 CSRF：

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/register`
- `POST /api/v1/auth/send-email-code`
- `POST /api/v1/auth/forgot-password`
- `POST /api/v1/auth/reset-password`

## 5. 核心枚举与数据模型

## 5.1 枚举

### 角色 `Role`

- `FRESHMAN`
- `LEADER`
- `ADMIN`

### 用户状态 `UserStatus`

- `ACTIVE`
- `DISABLED`

### 报名状态 `ApplicationStatus`

- `SUBMITTED`
- `GROUPED`
- `REJECTED`
- `WITHDRAWN`

当前代码中四种状态都已进入实际业务流转：

- `SUBMITTED`：已提交、待处理
- `GROUPED`：已进入分组
- `REJECTED`：在选拔期被管理员或负责人拒绝
- `WITHDRAWN`：在报名期由申请人主动撤回

### 年级 `Grade`

- `YEAR_1`
- `YEAR_2`
- `YEAR_3`
- `YEAR_4`
- `GRADUATED`

### 验证码场景 `EmailCodeScene`

- `REGISTER`
- `RESET_PASSWORD`

### 时期 `PeriodType`

- `REGISTRATION`
- `SELECTION`
- `INTERVIEW`
- `NOT_OPEN`
- `FINISHED`

其中：

- `REGISTRATION` / `SELECTION` / `INTERVIEW` 是可持久化配置的时期类型
- `NOT_OPEN` / `FINISHED` 是运行时推导状态，不会作为可配置时期写入数据库

## 7. 当前接口与流程的已知实现边界

1. 当前负责人可以查看所有未分组申请，而不是仅查看与自己分组条件相关的申请。
2. 当前方向树只实现两层结构。
3. 当前系统认证缓存仅支持 Redis，不能切换为内存实现。
4. 当前仍未实现自动分组、面试、任务提交、公告发布等后续业务。

## 8. 建议的前后端联调顺序

1. 配置好 MySQL、Redis、JWT 密钥、邮件服务。
2. 确认默认管理员是否需要自动初始化。
3. 先调用：
   - `GET /api/v1/meta/current-period`
   - `GET /api/v1/directions`
4. 报名期内完成：
   - 注册验证码发送
   - 注册
   - 登录
   - `GET /api/v1/auth/me`
5. 使用新生账号联调报名：
   - 创建报名
   - 查看报名列表
   - 查看报名汇总
