## 3. 技术栈与总体架构

### 3.1 基础框架

- Spring Boot 4.1.0
- Spring Security
- Spring Data JPA
- Spring Data Redis
- Flyway
- MySQL
- Jackson
- JavaMailSender

### 3.2 认证与权限总体方案

当前系统采用：

- `JWT + HttpOnly Cookie` 维护登录态
- `XSRF-TOKEN Cookie + X-CSRF-TOKEN Header` 进行 CSRF 校验
- `Spring Security 路由拦截 + 业务授权服务 AuthzService` 进行权限判断

### 3.3 缓存与安全状态管理

认证相关临时状态通过 `AuthCacheService` 抽象统一管理，当前已提供：

- `RedisAuthCacheService`

缓存内容包括：

- 邮箱验证码
- 验证码发送冷却状态
- 登录失败计数
- 登录锁定状态
- JWT 黑名单

当前版本只允许使用 Redis 作为认证缓存：

- 如果 `AUTH_CACHE_TYPE` 未配置，则默认按 `redis` 处理
- 如果显式配置成非 `redis`，系统会在启动阶段直接失败
- 如果 Redis 本身不可连接，系统也会在启动阶段直接失败

## 4. 已实现的功能模块

## 4.1 用户认证模块

入口控制器：

- `src/main/java/club/muimi/backend/controller/auth/AuthController.java`

核心服务：

- `src/main/java/club/muimi/backend/service/auth/AuthService.java`

已实现接口如下：

### 4.1.1 发送验证码

接口：

- `POST /api/v1/auth/send-email-code`

能力：

- 支持注册验证码发送
- 支持密码重置验证码发送
- 对同一邮箱和同一场景做发送冷却限制
- 注册场景下，如果邮箱已存在则返回统一成功响应但不发送邮件，避免账号枚举
- 找回密码场景下，不暴露邮箱是否存在，防止账号枚举

### 4.1.2 用户注册

接口：

- `POST /api/v1/auth/register`

能力：

- 校验用户名唯一
- 校验邮箱唯一
- 校验验证码正确且未过期
- 校验密码强度
- 密码使用 BCrypt 加密存储
- 注册完成后默认创建普通新生用户

### 4.1.3 用户登录

接口：

- `POST /api/v1/auth/login`

能力：

- 使用邮箱 + 密码登录
- 登录前校验账号是否被锁定
- 登录失败累计计数，达到阈值后临时锁定
- 登录成功后清除失败计数
- 登录成功后下发：
  - 登录 Cookie
  - CSRF Cookie

### 4.1.4 获取当前用户

接口：

- `GET /api/v1/auth/me`

能力：

- 返回当前登录用户基本资料
- 返回用户所属小组列表
- 返回用户是否是某个组的组长

### 4.1.5 退出登录

接口：

- `POST /api/v1/auth/logout`

能力：

- 清理登录 Cookie
- 将当前 JWT 放入黑名单直到自然过期

### 4.1.6 忘记密码

接口：

- `POST /api/v1/auth/forgot-password`

能力：

- 发送重置密码验证码
- 保持统一响应，避免暴露邮箱是否存在

### 4.1.7 重置密码

接口：

- `POST /api/v1/auth/reset-password`

能力：

- 校验验证码
- 校验新密码强度
- 重置密码后递增 `tokenVersion`
- 旧 Token 自动全部失效

### 4.1.8 已登录用户修改密码

接口：

- `POST /api/v1/auth/change-password`

能力：

- 校验旧密码
- 校验新密码强度
- 修改密码后递增 `tokenVersion`
- 当前 Token 进入黑名单
- 强制重新登录

### 4.2.2 JWT 机制

当前 JWT 中包含的信息包括：

- `sub`：用户 ID
- `role`：用户角色
- `tokenVersion`：Token 版本
- `jti`：JWT 唯一标识
- `iat`：签发时间
- `exp`：过期时间

当前实现特点：

- 自定义 HMAC SHA-256 JWT 实现
- 登录、改密、重置密码都与 `tokenVersion` 关联
- 旧 Token 可通过 `tokenVersion` 或黑名单失效

### 4.2.3 Cookie 机制

当前登录态通过 Cookie 保存：

- 登录 Cookie：`lab_recruit_token`
- CSRF Cookie：`XSRF-TOKEN`

登录 Cookie 特征：

- `HttpOnly`
- 支持 `Secure`
- 支持 `SameSite`

### 4.2.4 CSRF 防护

当前系统虽然禁用了 Spring Security 默认 CSRF 组件，但已经用自定义方式补齐防护。

方案为：

- 登录成功后签发一个与当前用户身份、`tokenVersion`、`jti` 绑定的 CSRF Token
- 前端写操作时必须同时提交：
  - `XSRF-TOKEN` Cookie
  - `X-CSRF-TOKEN` Header
- 仅在需要登录且可能修改状态的 API 上校验

当前对需要登录且可能修改状态的 API 统一校验 CSRF，包括登出、修改密码、报名写操作、分组、任务、公告、资料、通知已读、上传会话、管理端配置等接口。

### 4.2.5 业务授权服务

- 判断是否可管理某个组
- 判断是否可发布组公告
- 判断是否可访问任务

授权逻辑基于：

- 用户角色
- 申请归属
- 小组成员关系

## 4.4 默认管理员初始化模块

核心文件：

- `src/main/java/club/muimi/backend/config/DefaultAdminInitializer.java`
- `src/main/java/club/muimi/backend/config/DefaultAdminProperties.java`

能力：

- 应用启动时检查数据库中是否已经存在 `ADMIN` 角色用户
- 如果已经存在管理员，则跳过初始化
- 如果不存在管理员，则读取环境变量并自动创建一个默认管理员
- 默认管理员创建时直接设置为已验证邮箱用户，不经过邮箱验证码流程
- 如果默认管理员用户名或邮箱已被现有用户占用，则启动失败并给出明确错误
- 如果数据库中没有管理员且默认管理员环境变量未配置完整，则启动失败并给出明确错误

默认管理员相关环境变量包括：

- `DEFAULT_ADMIN_ENABLED`
- `DEFAULT_ADMIN_USERNAME`
- `DEFAULT_ADMIN_PASSWORD`
- `DEFAULT_ADMIN_EMAIL`

默认管理员的用途是保证系统在首次部署后具备一个可直接登录的管理入口，避免必须先通过普通注册流程再手工提权。

## 4.5 招新业务模块

当前业务模块已经实现，接口详情见 `document/当前后端流程与接口文档.md`。

### 4.5.1 报名申请

- 新生仅可在报名期创建、修改和撤回自己的申请
- 同一用户同一二级方向只能有一条申请
- 申请状态为 `SUBMITTED / GROUPED / REJECTED / WITHDRAWN`
- 申请被分组后不可再由本人修改或撤回
- 当前允许的报名年级由 `app.recruitment.application.allowed-grades` 配置

### 4.5.2 时期、方向和分组

- 管理员可配置 `REGISTRATION / SELECTION / INTERVIEW`
- `NOT_OPEN` 和 `FINISHED` 由系统推导，不允许人工配置
- 方向只支持两级结构
- 管理员可创建、修改、删除空分组
- 分组以报名申请为单位，申请加入分组时校验方向、年级、入学年份和容量
- 当前没有自动分组接口；管理员或负责人通过接口逐条分配
- 负责人可查看全局未分组申请列表，但只能把申请加入自己负责的分组

### 4.5.3 负责人指派

- 分组记录中通过 `leaderUserId` 指向负责人
- 被指派用户必须已经是 `LEADER` 且 `ACTIVE`
- 管理员可通过 `PATCH /api/v1/admin/users/{userId}/role` 将 `FRESHMAN` 提升为 `LEADER`
- 指派负责人本身不会自动修改用户角色
- 撤销负责人只清空分组 `leaderUserId`，不会自动把用户降回 `FRESHMAN`
- 管理员可通过角色修改接口将无负责分组绑定的 `LEADER` 降回 `FRESHMAN`
- 当前实现不强制负责人必须是该组成员，也不限制同一 `LEADER` 只能负责一个组

### 4.5.4 任务

- 任务必须绑定具体分组，不存在全局任务
- 管理员可管理任意组任务，负责人只能管理自己负责组任务
- 任务管理、提交、评测和打回均要求当前为选拔期
- 同一任务同一用户只有一条当前提交记录，状态为 `PENDING / SUBMITTED / REVIEWED`
- 已提交或已批阅后不能直接覆盖提交；需要负责人或管理员打回后重新提交
- 打回会清空当前提交内容、附件、提交时间、评测人、分数、评语和评测时间

### 4.5.5 公告、资料、文件、通知和审计

- 公告支持 `GLOBAL` 和 `GROUP`，全局公告仅管理员可发布
- 学习资料必须绑定具体分组，不存在公开资料或按方向资料
- 文件上传先生成未绑定 `StoredFile`，业务绑定时校验上传人、用途和未绑定状态
- 站内通知覆盖申请分组/拒绝/取消分组、任务发布/打回/评测、公告发布和资料发布
- 关键写操作写入审计日志，管理员可查询审计日志

### 4.5.6 看板和导出

- 管理员可查看全局总览和所有分组看板
- 负责人可查看自己负责分组看板
- 支持导出报名信息、分组成员和分组任务结果，格式为 Excel

## 5.3 JWT 配置

- `JWT_SECRET`
- `JWT_COOKIE_SECURE`
- `JWT_COOKIE_SAME_SITE`

### 5.3.1 JWT 启动校验

当前会在启动时校验：

- 密钥不能为空
- 密钥长度至少 32 个字符
- Cookie 名称不能为空
- CSRF Header / Cookie 名称不能为空
- `SameSite=None` 时必须启用 `Secure`

## 5.4 认证业务配置

- 验证码有效期
- 验证码发送冷却时间
- 登录失败阈值
- 登录锁定时间
- 缓存实现类型

### 5.4.1 Redis 启动校验

当前启动时会显式校验：

- `app.auth.cache-type` 必须为 `redis`
- Redis 必须可以连通
- Redis `PING` 必须返回 `PONG`
- Redis 必须允许写入；启动阶段会写入一个带短 TTL 的临时探针键并立即删除

如果以上任一条件不满足，应用会直接启动失败，而不是等到登录或注册时再返回 `500`

## 5.5 默认管理员配置

- `DEFAULT_ADMIN_ENABLED`
- `DEFAULT_ADMIN_USERNAME`
- `DEFAULT_ADMIN_PASSWORD`
- `DEFAULT_ADMIN_EMAIL`

行为说明：

- 当数据库中没有管理员用户时，系统会使用上述配置自动创建默认管理员
- 当数据库中已有管理员用户时，上述配置不会重复创建新管理员
- 默认管理员创建时不需要邮箱验证
- 如果要彻底关闭这项能力，可将 `DEFAULT_ADMIN_ENABLED=false`

## 8. 当前项目的实现边界

当前项目已经具备可联调的后端业务主流程。当前保留的实现边界如下：

- 方向只支持两级结构。
- 当前没有自动分组接口，也没有拖拽式移动接口；分组通过接口逐条分配。
- 负责人指派不会自动修改用户角色；管理员可通过用户角色接口将 `FRESHMAN` 提升为 `LEADER`，也可在目标用户无负责分组绑定时将 `LEADER` 降回 `FRESHMAN`。
- 当前不强制负责人必须是该组成员，也不限制一个负责人只能负责一个组。
- 负责人可查看全局未分组申请列表，但只能操作自己负责的分组。
- 任务和学习资料都是组级资源；任务没有全局任务，资料没有公开资料或按方向资料。
- 任务提交不保留历史版本；同一任务同一用户只有一条当前提交记录。
- 打回任务提交会清空原提交内容和附件。
- 文件存储使用本地磁盘，不是对象存储。
- 分片上传只支持严格顺序上传，不支持乱序分片、秒传或断点恢复。
- 当前前端仍是单文件联调页面，不是正式 Vue 工程。

### 当前注意事项

1. 项目启动前必须配置 `JWT_SECRET`
2. 邮件服务启动前必须配置 SMTP 环境变量
3. 如果数据库中尚无管理员，则还必须配置默认管理员环境变量，或显式关闭该功能

5. MySQL 当前可运行，但 5.7 版本存在 Hibernate / Flyway 的兼容性警告，建议后续升级到 8.0+
